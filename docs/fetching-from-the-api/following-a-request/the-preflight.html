The Preflight

A request with an Authorization header makes the browser ask the API's permission first, with an OPTIONS request your code never sees.

With the Network tab open on /tickets/2, change the filter from Fetch/XHR to All, and reload. Two more requests appear, whose Type is preflight and whose method is OPTIONS: one sent just before each GET (two GETs, because of StrictMode). Fetch/XHR hid them, because your JavaScript didn't send them. The browser did.

Asking first

Stage 0's request to /welcome didn't need a preflight. This one carries an Authorization header, and a browser won't send that header to another origin without asking first (Stage 0, topic 01, "CORS From the Other Side").

So before the real request, the browser sends an OPTIONS request that asks: "may a page from localhost:5173 send a GET with an authorization header?" The API's cors() answers:

204 No Content
Access-Control-Allow-Origin: *
Access-Control-Allow-Headers: authorization

Only then does the browser send the GET. If the API said no, the GET would never be sent, and fetch() would fail as if the API weren't there.

The browser remembers the answer for a few seconds, so you won't see a preflight before every request.

Not your code's job

None of this is in client.js. fetch() asks for one request, and the browser decides whether it needs to ask permission first. That's why the Fetch/XHR filter is the one to use when you're following your own code's requests.

Try it

Click one of the preflight rows. What's its Status Code? Under Response Headers, find Access-Control-Allow-Headers. Which line in the back-end's app.js put it there?
