Watching It in the Network Tab

The browser's Network tab shows steps 6 and 7 of the trace for real: the request, its token, the status and the JSON that came back.

Steps 6 and 7 of the trace happen between the browser and the API, so you can't see them in the code. The browser records them, though. Open the developer tools (F12), choose the Network tab, click Fetch/XHR so it lists only requests made by JavaScript, and open http://localhost:5173/tickets/2.

What to look at

Click a request named 2 and read its Headers:

  • Request URL http://localhost:3000/tickets/2: API_URL from .env, plus the path getTicket() built (topic 03).
  • Request Method GET: apiRequest()'s default.
  • Status Code 200 OK, or 304 Not Modified as in the screenshot: the answer step 7 sent. See below for 304.
  • Request Headers, Authorization: Bearer eyJ...: the header buildHeaders() added, with your token from .env.

Then click Response (or Preview, which lays it out as a tree). That's the JSON { "data": { ... } } that apiRequest() read, and getTicket() unwrapped.

304 Not Modified

The first time the browser asks for ticket 2, the API answers 200 with the JSON, plus an ETag header: a short fingerprint of that JSON (Express adds it). The browser keeps a copy of the response.

Next time, the browser sends the fingerprint back, in the If-None-Match header you can see in the screenshot. If the ticket hasn't changed, the API answers 304 Not Modified with no body, and the browser uses its copy.

Your code never sees the 304. fetch() hands apiRequest() the copy, as a 200, so response.ok is true and nothing in client.js needs to know about it. To see 200 every time while you investigate, tick Disable cache at the top of the Network tab.

Why two requests?

In development, StrictMode runs every effect twice, so the page asks for the ticket twice. The first request's answer is ignored by the ignore flag (Stage 0, topic 06). A production build sends one.

Try it

With the Network tab open, open /tickets/999. What colour is the request, and what's its status? Click Response: which part of it did the page use? Then open /tickets. How many requests for tickets are there, and what's in the meta of the response?
