Tracing a Ticket

Every step from clicking a ticket to seeing it, through each file, across to the API and back, including the way back when there's no such ticket.

Stage 0 traced the starter's home page, from a click to the API's message (Stage 0, topic 06). Here's the same trace for a ticket. It has the same shape, with three new things: a value from the URL, a token, and two ways back.

What's new since Stage 0

  • Step 3: the URL. useParams() reads '2' from the URL (Stage 1). It's the only reason the page knows which ticket to ask for.
  • Step 6: the token. buildHeaders() adds Authorization: Bearer ..., because getToken() now returns VITE_DEV_TOKEN (topic 02).
  • Step 7: the back-end you built. The request passes through the same layers you wrote: the authenticate middleware (Lesson 4), the ID's validation (Lesson 3), then the controller, the service and Prisma. A failure at any of these ends the request early, with its own status: 401, 400 or 404.
  • Two ways back. On a 200, the data comes back up as a return value. On a 404, it comes back up as a thrown error. Both end in the page's state, and both end in a re-render.

Where the layers line up

Each front-end layer has a partner in the back-end:
