The Same Pages, Real Data

Stage 2 keeps every page from Stage 1, and changes only where their tickets come from: the API, instead of a hard-coded array.

At the end of Stage 1, the app had a list of tickets and a page for each ticket. Both showed tickets from a hard-coded array, sampleTickets.js, whose top comment said TEMPORARY.

Stage 2 deletes that array. The same two pages now ask the Support Desk API for their tickets:

URL Page Asks the API for
/ HomePage nothing (unchanged)
/tickets TicketListPage GET /tickets
/tickets/2 TicketDetailPage GET /tickets/2
anything else NotFoundPage nothing (unchanged)

You've seen this move before. In the back-end, Lesson 1 kept the tickets in an in-memory array, and Lesson 2 swapped it for Prisma queries against MySQL. Stage 1 was the front-end's Lesson 1. This is its Lesson 2.

What's new: waiting, and failing

With the array, the tickets were there the moment the page appeared, and nothing could go wrong. A request to the API is different:

  • it takes time, so the page needs something to show while it waits
  • it can fail: the API isn't running, the token is wrong, or the ticket doesn't exist
  • it can come back empty: a customer with no tickets gets []

So each page now has the states you met in the starter's HomePage: loading, error and success, plus "empty" for the list. The pattern is the same one, applied to tickets.
