When the Ticket Isn't There

getTicket() has no error handling of its own. The API's 404 or 400 becomes an error with a status, and it passes straight through to the page.

In Stage 1, a missing ticket was easy to spot: find() returned undefined. Now the API decides, and it answers with a status code.

Try a few IDs in your REST client with Ada's token:

Request Status error.message
GET /tickets/2 200 (ticket 2, in data)
GET /tickets/999 404 Ticket 999 not found
GET /tickets/abc 400 Validation failed
GET /tickets/0 400 Validation failed
GET /tickets/2.0 200 (ticket 2: the validation reads 2.0 as the number 2)

The 400s come from the back-end's Zod validation (Lesson 3): abc isn't a number, and 0 isn't a positive one, so those requests never reach the database. (z.coerce.number() is also what turns the text 2.0 into the number 2.) For a customer, a 404 can also mean "it exists, but it isn't yours": Lesson 4 made the API answer that way on purpose, so it doesn't reveal which tickets exist ("Hiding What You Can't See").

The error passes through

getTicket() has no try/catch, and it doesn't need one. On any status that isn't 2xx, apiRequest() throws an error that carries the status and the API's message (Stage 0, topic 05):

// Figure 2.6: turning a status into an error (src/api/client.js, excerpt)
if (!response.ok) {
  const message = responseBody?.error?.message
    || `Request failed with status ${response.status}`;
  throw createApiError(
    response.status, message, responseBody?.error?.details
  );
}

(The file has the message and throw lines on one line each. They're split here to fit.)

When apiRequest() throws, await in getTicket() throws the same error, so getTicket() stops there and the error carries on up to the page that called it, still holding error.status.

Who decides what it means?

Not tickets.api.js. Whether a 404 should say "Ticket not found", or whether a 400 should count as "not found" too, is about what the user sees, and that's a page's job. Topic 05 shows how TicketDetailPage uses error.status to choose.

The API module's job is only to ask, and to let the answer through unchanged, good or bad.

Try it

Send GET /tickets/abc again and look at the whole response body, not just the message. What else is in error? apiRequest() keeps that part too, as error.details. Nothing uses it in this stage. What kind of page do you think will need it?
