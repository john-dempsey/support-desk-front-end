Your Stage 2 Checklist

The same steps for your own case study: your API running, an API module, pages that load data, and tests for every state.

At the end of Stage 1, your own front-end had a list page and a detail page, showing a hard-coded array. Here's how to load the real data, using the steps Stage 2 took. The examples use a booking system; swap in your own entity.

Run npm test and look at the page in the browser after every step, and commit when both work.

1. Your API, and a token if it needs one

Start your API, and send GET /bookings in a REST client. Does it answer 200, or 401?

  • 401: your API has authentication. Log in with a REST client, put the token in .env as VITE_DEV_TOKEN, and add the line, empty, to .env.example, with a TEMPORARY comment. Change getToken() in client.js to return it (Figure 2.3).
  • 200: your API has no authentication. Leave getToken() alone. No header is sent, and nothing else changes.

2. An API module

src/api/bookings.api.js, with getBookings() and getBooking(id), each returning responseBody.data (Figure 2.5).

3. The list page

In BookingListPage.jsx, replace the sample array with three pieces of state (the list starting as null), and an effect with the ignore flag (Figures 2.7 to 2.9). Your list component shouldn't change.

4. The detail page

In BookingDetailPage.jsx: the same pattern, with [bookingId] and a cleanup that resets the state (Figures 2.11 to 2.13), and early returns for each state.

Before you write the catch, find out what your API answers. In a REST client, try /bookings/99999, /bookings/abc and /bookings/0. Which statuses come back? Decide which of them mean "not found" to your user.

5. Delete the sample data

Delete src/data/sampleBookings.js once nothing imports it. Search for its name to check.

6. Tests

  • src/test/testBookings.js, in your API's shape, named for the cases they cover.
  • bookings.api.test.js, faking client.js (Figure 2.17).
  • One test per state for each page (Figures 2.18 to 2.21), and the URL change test if your detail page has the cleanup.
  • Fake bookings.api.js in App.test.jsx, and use findBy for anything that appears after loading.
  • If you changed getToken(): vi.stubEnv in the "no token" test, and unstubEnvs: true in vite.config.js (Figures 2.24 and 2.25).

7. Watch it work

Open the Network tab and click through your pages. Is every request the one you expected? Does each have an Authorization header (if your API needs one)?
