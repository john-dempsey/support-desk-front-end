getToken()

One small function in client.js now returns the token from .env. It's the only change to the API client in this stage.

Stage 0's API client already knew how to send a token. It just never had one: getToken() returned null (Figure 0.15). Stage 2 changes that one function:

// Figure 2.3: where the token comes from (src/api/client.js, excerpt)
export function getToken() {
  return import.meta.env.VITE_DEV_TOKEN || null;
}

If .env has a token, getToken() returns it. If the setting is empty or missing, import.meta.env.VITE_DEV_TOKEN is '' or undefined, and || null turns either of those into null, the same "no token" value as before.

The rest of the client is unchanged

buildHeaders() is exactly as it was in Stage 0:

// Figure 2.4: the headers, unchanged (src/api/client.js, excerpt)
function buildHeaders(hasBody) {
  const headers = {};

  if (hasBody) {
    headers['Content-Type'] = 'application/json';
  }

  const token = getToken();
  if (token) {
    headers.Authorization = `Bearer ${token}`;
  }

  return headers;
}

Every request goes through apiRequest(), and apiRequest() calls buildHeaders(). So once getToken() returns a token, every request carries an Authorization: Bearer ... header, without a single page knowing about it. That's the header the back-end's authenticate middleware reads.

A stand-in, like customerId

The back-end did the same thing in Lesson 2. With no authentication yet, createTicket took a customerId from the request body, a stand-in marked as temporary, until Lesson 4 replaced it with req.user.id.

VITE_DEV_TOKEN is the front-end's stand-in. In Stage 4, getToken() will return the token of whoever logged in, and VITE_DEV_TOKEN will be deleted. Nothing else in client.js will change.

If your API has no authentication

Leave VITE_DEV_TOKEN empty. getToken() returns null, no Authorization header is sent, and every page works exactly the same. That's why Stage 0 built the client to add the header only when there's a token.
