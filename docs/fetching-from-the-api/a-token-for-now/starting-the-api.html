Starting the API

From now on the front-end needs the Support Desk API running, with its database migrated and seeded.

Stage 1 didn't need the API at all. From this stage on, the ticket pages get everything from it, so it has to be running first.

The API

Since Lesson 6, the whole back-end runs in Docker: MySQL, Redis, Mailpit, the API and the worker. In the back-end's folder (support-desk-student), start them all, then set up the database from inside the API's container:

docker compose up -d
docker compose exec api npx prisma migrate deploy
docker compose exec api npm run db:seed
  1. Start every container in the background (-d). The first time, Docker builds the API's image from its Dockerfile first, which takes a minute. The API is then on http://localhost:3000.
  2. Migrate: create the tables. Only needed the first time, or after a new migration.
  3. Seed: fill the tables with the sample users and tickets. The seed deletes everything first, so running it again puts the tickets back the way they started.

docker compose exec api runs a command inside the running api container, where the API's code and node_modules are. Prisma connects to MySQL from there, the same way the API does.

Migrating uses migrate deploy, not npm run db:migrate. The script runs migrate dev, which is for creating new migrations while you change the schema, and it fails inside the container. migrate deploy only applies the migrations that already exist, which is all that's needed here.

If you've changed the back-end's code since its image was built, add --build (docker compose up -d --build) so the container runs your latest code.

The front-end

In a second terminal, in this project's folder:

npm install
cp .env.example .env
npm run dev

npm install is only needed the first time, or when package.json changes. If you made a .env in Stage 0, skip the cp, which would overwrite it. The app is on http://localhost:5173.

Ask the API first

Before involving the front-end, check that the API answers. In a REST client, send:

GET http://localhost:3000/tickets

The answer is not a list of tickets:

401 Unauthorized

{ "error": { "message": "Authentication required" } }

In Lesson 4, the back-end's authenticate middleware went in front of every route except /auth/register and /auth/login. A request with no Authorization header never reaches the ticket controller.

Try it

Open http://localhost:5173/tickets. The page isn't broken: it shows the same message as the REST client. Where did the page get that text from? (Hint: Stage 0's apiRequest() reads error.message from the response.)
