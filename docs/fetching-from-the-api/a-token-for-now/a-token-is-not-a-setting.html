A Token Isn't a Setting

Stage 0 said a front-end can't keep a secret. VITE_DEV_TOKEN breaks that rule on purpose, so it's only safe on your own machine, and only for now.

Stage 0 ended its slide on .env with a rule: a front-end can't keep a secret. Vite copies every VITE_ value into the JavaScript it sends to the browser, where anyone can read it.

A token is a secret. While it lasts, it works like Ada's password: anyone who has it can send requests as Ada, an admin. And VITE_DEV_TOKEN is copied into the code exactly like VITE_API_URL. Run npm run build with a token in .env, search the files in dist/assets/, and you'll find the whole token in the JavaScript.

So VITE_DEV_TOKEN breaks Stage 0's rule, on purpose. That's acceptable only because of where and how long it's used:

  • Only on your machine. The app runs on localhost, against an API on localhost, with seeded users whose password is password123. There's nothing real to steal.
  • Never committed. It lives in .env, which git ignores. Only the empty line in .env.example is committed.
  • Never deployed. Don't put a build made with a token anywhere other people can reach it.
  • Only until Stage 4. Then each user logs in and gets their own token, and VITE_DEV_TOKEN is deleted.

Tokens run out

A JWT has an expiry time inside it. The Support Desk API's tokens last one day, so tomorrow every request will fail with 401 Invalid or expired token. The fix takes a minute: log in again with your REST client and paste the new token into .env.

When the Tickets page shows an error

Message What it means
Can't reach the API at http://localhost:3000 — is the back-end running? The API isn't running, or VITE_API_URL is wrong
Authentication required VITE_DEV_TOKEN is empty or missing
Invalid or expired token The token was copied wrongly, or it has expired. Log in again
