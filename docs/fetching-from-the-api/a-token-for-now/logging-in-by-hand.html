Logging In by Hand

There's no login page until Stage 4, so you log in once with a REST client and keep the token it sends back.

To see tickets, a request needs a token. A token comes from logging in. The front-end has no login page yet: that's Stage 4.

So for Stages 2 and 3, you log in once, by hand, with a REST client, the same way you tested the back-end in Lesson 4.

The request

POST http://localhost:3000/auth/login
Content-Type: application/json

{ "email": "ada@example.com", "password": "password123" }

The response

{
  "data": {
    "user": {
      "id": 1,
      "name": "Admin Ada",
      "email": "ada@example.com",
      "role": "admin",
      "createdAt": "2026-10-14T17:08:18.426Z"
    },
    "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIi..."
  }
}

The token is a JWT, the same kind the back-end's jwt.js signs: a long string in three parts, separated by dots. Your token, id and date will be different. Copy the token without the quotes around it.

Why Ada?

Lesson 4 made the API decide which tickets each person sees. Customers see only their own, agents see theirs and the unassigned queue, and admins see every ticket. Ada is an admin, so her token shows the whole picture while you build the pages.

Any seeded user works (they all use password123). The pages don't check who you are; the API does.

If you get a 429

The API allows only 10 login attempts every 15 minutes from one computer, to slow down anyone guessing passwords. If a login returns 429 Too Many Requests (the message is "Too many requests — please try again later."), wait a few minutes and try again. You only need one token, so this shouldn't happen often.

Try it

Log in as Ada and keep the token: you'll need it on the next slide. Then send GET http://localhost:3000/tickets again, this time with an Authorization header whose value is Bearer, a space, and the token. How many tickets come back? What's in meta?
