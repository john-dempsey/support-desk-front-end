One Test per State

The list page has four states, and the fake API can put it in each one: waiting, success, empty and failed.

Stage 0's HomePage test showed how to make a fake API module answer with data (mockResolvedValue) or never answer (mockReturnValue with a promise that never settles). TicketListPage.test.jsx uses both, and adds the other two states the page can be in:

State The fake The test expects
waiting getTickets.mockReturnValue(new Promise(() => {})) "Loading tickets…"
success getTickets.mockResolvedValue(testTickets) a link for each ticket
empty getTickets.mockResolvedValue([]) "There are no tickets to show."
failed getTickets.mockRejectedValue(new Error(...)) the error message

Here are the last two:

// Figure 2.18: empty and failed (src/pages/TicketListPage.test.jsx,
// excerpt)
  it('shows a message when the API sends no tickets', async () => {
    getTickets.mockResolvedValue([]);

    renderWithProviders(<TicketListPage />);

    expect(
      await screen.findByText('There are no tickets to show.'),
    ).toBeInTheDocument();
  });

  it("shows the API's error message when the request fails", async () => {
    getTickets.mockRejectedValue(new Error('Invalid or expired token'));

    renderWithProviders(<TicketListPage />);

    expect(await screen.findByRole('alert')).toHaveTextContent(
      'Invalid or expired token',
    );
    expect(screen.queryByRole('table')).not.toBeInTheDocument();
  });

(The two expects with await are one line each in the file. They're split here to fit.)

mockRejectedValue

mockRejectedValue(error) is the opposite of mockResolvedValue: the fake getTickets() throws that error when it's awaited, just as the real one does when apiRequest() throws. So the page's catch runs, with no API to break.

Checking what's missing

The failed test checks two things: the message is there, and the table isn't. queryByRole returns null instead of throwing when nothing matches (Stage 0, topic 08), which is what you want when you're checking that something is absent.

That second check is the null from topic 04 at work: after a failure, tickets is still null, so TicketList is never shown.

Each test makes the API do one thing

None of these tests needs a running API, a token or a network. Making a real API fail on demand, or answer slowly enough to see "Loading…", is hard. Making a fake do it takes one line.

Try it

In TicketListPage.jsx, change useState(null) to useState([]) for tickets (as in topic 04's "Try it"), and run npm test. Every test still passes, but the page now says "There are no tickets to show." while it's loading. The tests have a gap.
