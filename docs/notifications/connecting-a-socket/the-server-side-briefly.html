The Server Side, Briefly

You built the other end in the back-end: a socket says who it is by sending its token, joins its user's room, and receives notification.created.

You wrote the server's half of this in the back-end, so here's just what the browser has to do to fit it. This is the API's config/socket.js since Lesson 8, "The New Socket Contract":

io.on('connection', (socket) => {
  socket.on('authenticate', (token) => {
    try {
      const { sub } = verifyToken(token);
      socket.join(`user:${sub}`);
    } catch {
      socket.disconnect();
    }
  });
});

The contract

The server… So the browser must…
doesn't know who a new connection belongs to send authenticate with its token, after connecting
puts a verified socket in one room, user:<id> (nothing: it only ever hears about its own user)
disconnects a socket with a bad token log in again; the next connection sends a good one
pushes one event, notification.created, with the saved notification listen for that event name

There's no Authorization header on a socket (Lesson 5, "Authenticating a Socket with the Existing JWT"), so the token goes in a message instead. It's the same token client.js sends with every HTTP request, from the same place: getSavedToken().

Rooms belong to a connection

socket.join() puts this connection in a room. If the connection drops and a new one is made, the server sees a brand-new socket, in no rooms at all. That one fact shapes the next two slides.

The browser's half

The front-end's side lives in one new file, src/realtime/socket.js, with three functions:

Function Does
connectSocket() connects, and sends authenticate with the saved token on every connect
disconnectSocket() disconnects, on logout
onNotification(handler) calls handler with each push; returns a function that stops it

Nothing else in the app imports socket.io-client, the same way nothing but client.js calls fetch().
