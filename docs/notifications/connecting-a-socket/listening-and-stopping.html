Listening, and Stopping

onNotification() adds a handler for notification.created, and gives back the function that removes it: exactly what an effect's cleanup needs.

The last function lets a component hear about pushes:

// Figure 5.14: listening for notifications
// (src/realtime/socket.js, excerpt)
// Calls `handler` with each new notification as it arrives. Returns a
// function that stops listening, for a component's effect cleanup:
//   const stopListening = onNotification(handleNotification);
//   return stopListening;
export function onNotification(handler) {
  socket.on('notification.created', handler);
  return () => {
    socket.off('notification.created', handler);
  };
}

socket.on('notification.created', handler) asks the socket to call handler with the notification each time the server pushes one. A socket can have any number of handlers for the same event, and calls every one of them:

A function that returns a function

onNotification() returns an arrow function. That function remembers the handler it was created with, so calling it later removes exactly that handler and no other. Whoever started listening doesn't need to keep the handler, or know how the socket stores it: they keep the one function that undoes what they did.

An effect's cleanup is exactly that kind of function, "undo what this effect did". So a component can hand it straight back:

useEffect(() => {
  const stopListening = onNotification(handleNotification);
  return stopListening;
}, []);

Compare it with the ignore flag in every fetching effect: there, the cleanup undoes "a response might still arrive". Here it undoes "I'm listening".

Why stop?

A handler that's never removed stays on the socket for as long as the app is open. Each time a page that listens opened, it would add another, so one push would run the code of every visit that page had ever had. The provider (next slide) and, later in this lesson, three pages listen, and all four stop when they're done.
