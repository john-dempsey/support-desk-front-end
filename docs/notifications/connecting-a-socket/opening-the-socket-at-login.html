Opening the Socket at Login

The provider's effect gains four lines: connect when a user logs in, re-fetch the count on each push, and stop listening and disconnect in the cleanup.

NotificationsProvider already runs an effect whenever the user changes (topic 03). That's exactly when the socket should open and close, so Part 2 adds its lines to the same effect. Here's the rest of it, below the loadUnreadCount() function:

// Figure 5.15: the socket joins the effect
// (src/context/NotificationsProvider.jsx, excerpt)
    // 1. History over REST: everything not read yet, including what
    //    arrived while the user was away.
    loadUnreadCount();

    // 2. Live updates over the socket: each push means a new unread
    //    notification. Asking the API again, instead of adding 1, keeps
    //    the API as the truth. The API saves a notification before it
    //    pushes it, so the new one is always in the answer.
    connectSocket();
    const stopListening = onNotification(() => {
      loadUnreadCount();
    });

    // When the user logs out (user becomes null) or changes: stop
    // listening and close the socket, so nobody gets someone else's
    // pushes, and forget the old user's count.
    return () => {
      ignore = true;
      stopListening();
      disconnectSocket();
      setUnreadCount(0);
    };
  }, [user]);

This is the stage-05 code. The top of the effect is as in Figure 5.9, and the if (user === null) comment now ends "and no socket to open".

What the four new lines do

Line When Does
connectSocket() someone logs in opens the socket; it sends the saved token on connect
onNotification(() => { loadUnreadCount(); }) each push asks the API for the count again
stopListening() logout, or another user removes that handler
disconnectSocket() logout, or another user closes the socket

connectSocket() needs no token passed in: socket.js reads the saved one itself (slide 03, "Telling the Server Who You Are, Every Time"). The provider only decides when.

A push means "count again"

When a push arrives, the handler calls loadUnreadCount(): the same function that loaded the count at login, with the same ignore check. It doesn't add 1. The next topic follows a push all the way from Casey's click to Alex's count, and shows why counting again is always right.

Logging out

Logging out sets user to null. React runs the cleanup from the logged-in run, which stops listening, closes the socket and sets the count to 0. Then the effect runs with null, and returns at once. The next user to log in gets a new connection, which sends their token.

Try it

Open the Network tab and choose the Socket filter. Log in as Alex: a row appears. Log out, then log in as Casey. How many rows are there now? Click the newest one and open its Messages. Which line of Figure 5.15 opened that connection, and which line closed the one before it?
