Five Requests to Open a Socket

Socket.IO starts with ordinary HTTP requests, then switches to a WebSocket. In Chrome, the token goes in one of the HTTP requests, before the switch.

"The socket" sounds like one connection. In the Network tab it's several requests. Open the developer tools, choose the Network tab with All selected, type socket.io in the filter box, and log in as Alex. Five rows appear:

Row Type What it is
1, 2, 4, 5 xhr ordinary HTTP requests to /socket.io/?EIO=4&transport=polling…
3 websocket the WebSocket, to /socket.io/?EIO=4&transport=websocket…

HTTP first, then a WebSocket

Socket.IO doesn't open a WebSocket straight away. It starts with ordinary HTTP requests, which work on any network, and uses them to agree a session with the server. Then it opens a WebSocket (row 3), checks that it works, and moves over to it. If a WebSocket can't be opened, say a firewall blocks it, Socket.IO carries on over HTTP, and your code doesn't notice. That fallback, and reconnecting by itself, are why the back-end chose Socket.IO over a bare WebSocket (Lesson 5, "Socket.IO: a WebSocket Library").

The Socket filter (next to Media and Manifest) shows only WebSockets: row 3, and one more for each later connection. It also shows a row named ?token=…. That one isn't the app's: it's Vite's own WebSocket, which npm run dev uses to update the page when you save a file, and its "token" is Vite's, not your login token.

Where the token went

socket.js sends authenticate as soon as the connect event fires. In Chrome, connect fires before the move to the WebSocket has finished, so the token goes in an HTTP request: row 5, a POST. Click it and open Payload:

42["authenticate","eyJhbGciOiJIUzI1NiIs…"]

That's Socket.IO's own format, with the token cut short here:

  • 4: a message (rather than, say, a ping)
  • 2: an event, followed by its name and data as a JSON array

So socket.emit('authenticate', token) becomes 42["authenticate", token]. The server reads it back as the authenticate event, whichever way it arrived.

Try it

Log in as Alex with the Network tab open as above.

  1. Click row 1 and open its Response. Can you find a sid (session ID)? Do rows 2, 4 and 5 send it back in their URLs?
  2. Find the authenticate message in row 5's Payload. Compare the token in it with the one in Application → Local storage. Which line of socket.js put it there?
