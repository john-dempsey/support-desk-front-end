When the Connection Ends

Restart the API and the socket reconnects and sends the token again by itself. Log out and it closes. A bad token makes the server close it, and it stays closed.

A socket stays open for as long as someone is logged in, so it meets things a single request never does. Three are worth watching in the Network tab (All, filtered to socket.io).

The API restarts

Run docker compose restart api in the back-end's folder. The WebSocket row stops, and a few seconds later a new set of rows appears: Socket.IO has reconnected by itself, with no code of ours involved. Look for authenticate again in the new rows. That's sendToken() running on the new connect event, so the new connection joins Alex's room (topic 04, slide 03). Have Casey comment: the push still arrives.

Logging out

Log out, then log in as someone else. disconnectSocket() closed the old connection when user became null, and the next login opened a new one, with the new user's token. Pushes for the old user can't reach this browser any more.

A token the server rejects

The server disconnects a socket whose token doesn't verify. Socket.IO treats that as deliberate: when the server closes the connection, it doesn't try to reconnect. So a bad token gives no pushes, and no flood of retries either.

The app doesn't need to handle this on the socket. The same token is sent with every HTTP request, so the next request gets a 401, and client.js logs the user out (Stage 4, topic 09). After the next login, a good token opens a new socket.

Try it

  2. Log in as Alex. In Application → Local storage, change one character of the saved token. Don't reload. Restart the API, and watch the rows: does the socket come back, and does it keep trying? Then click Tickets. What happens, and which file did it?
