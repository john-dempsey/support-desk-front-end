Your Stage 5 Checklist

The same steps for your own case study: history over REST first, then a socket, the count, live updates and a notice on the pages that show the records.

Only if your API has notifications (and a login). If it doesn't, your app is complete at Stage 4, or at Stage 3 (topic 01).

Here's how to add Stage 5 to your own front-end, in the order this lesson did it: everything that works over REST first, then the socket on top. The examples use a booking system; swap in your own names. Run npm test and try the app in the browser after every step, and commit when both work.

0. Check your API

In your REST client, and in your back-end's code, find out:

  • the route for a user's own notifications, and what each one looks like. Is there a "read" field like readAt? A link to the record it's about, like ticketId?
  • the route to mark one as read, if there is one.
  • whether you can ask for unread only. If not, count them in the browser: notifications.filter((n) => n.readAt === null).length.
  • what your socket expects: the name of its "who are you" event (authenticate here), and the name of the event it pushes.
  • what a push carries. If it's the saved notification, as in Lesson 8, you can add it to the list. If it's something else (say, the record that changed, as Lesson 5's pushes were), use the push only as a nudge, and load the list again.
