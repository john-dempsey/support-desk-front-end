Try It Yourself

Challenges that use everything in this lesson. Run the tests after each one, and commit when they pass.

Each of these builds on something from this lesson. After each one, run npm test and npm run lint, and commit when both pass.

Warm-up

  1. Mark all as read. Add a Mark all as read button to the notifications page. There's no route for it, so send one PATCH /notifications/:id/read for each unread notification. Should they go one at a time, or all at once with Promise.all() (Stage 3, topic 05)? Refresh the count once, at the end. Test it.
  2. Unread only. Add an "Unread only" checkbox to the notifications page that loads getUnreadNotifications() instead. Keep the choice in the URL (/notifications?unread=true) with useSearchParams(), as the ticket list does, so it survives a reload.

Build something

  1. A pop-up. When a notification arrives, show its message for a few seconds, on whatever page the user is on. Which component should listen, so it works on every page? Put the message in an aria-live="polite" region. Hide it with setTimeout(), and clear the timer in the effect's cleanup. Test it with captureNotificationHandler().
  2. Catch up after a reconnect. A push sent while the socket was down is lost (topic 01, slide 02). Add an onReconnect(handler) to socket.js, shaped like onNotification(), and use it in the provider to refresh the count whenever the socket connects again. Test it with the fake socket's fire('connect').
  3. Reload quietly. Make the detail page reload the ticket and its comments by itself when a notification arrives, without losing a comment that's being typed. (Hint: the page goes back to "loading" because the fetch effect's cleanup sets isLoading. A quiet reload needs a fetch that doesn't.) What should happen if the new data arrives while a comment is being saved?
  4. The missing test. Write the test from topic 08, slide 06: mark a notification as read, push another before the PATCH answers, then let it answer. Check your test fails with the plain form in handleMarkRead, and passes with the function form.

Investigate

  1. Two tabs. Log in as Alex in two tabs. Have Casey comment: does each tab get the push? Now mark a notification as read in the first tab. What does the second tab's count say? When does it correct itself, and why then?
  2. Ada's list. Log in as Ada and open Notifications. What's there, and which process created it? Why did none of it arrive over the socket?
  3. One more for the author. As Alex, assign an unassigned ticket to Alex. Alex's count goes up. Find the code in the back-end that chose to tell Alex about something Alex did. Would you change it?

Commit

git add .
git commit -m "Stage 5: mark all as read, a pop-up, ..."

When your own case study's users can see their notifications and mark them read, see an unread count on every page, get new ones live without a reload, and are told when the record on their screen has changed, with tests for each, your front-end has caught up with your back-end's notifications.
