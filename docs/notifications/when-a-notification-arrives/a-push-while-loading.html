A Push While the List Is Loading

If a push arrives before the list has loaded, the handler leaves the list as null: the load that's on its way will almost always include the new notification anyway.

Figure 5.16 has one more case to explain:

if (currentNotifications === null) {
  return null;
}

null means "not loaded yet" (Figure 5.3). A push can arrive in that moment: Alex opens Notifications just as Casey comments. What should the handler do?

Leave it alone

Returning null keeps the page in its loading state, so the request that's on its way can fill the list as normal. Making a list of one instead, [newNotification], would show a single notification, then have it replaced by the whole list a moment later.

Usually, nothing is lost. The API saves the notification before pushing it (slide 02), so the list request, if the API answers it after the save, already includes the new one.

The one gap

If the API answered the list request in the instant before the save, the answer doesn't include the new notification, and the push that announced it was ignored. That notification is missing from the page until it's next opened. It's still saved, and still counted in the navigation bar.

That needs a request and a save to land within milliseconds of each other, so it's very rare, and it fixes itself next time. The code's comment says so. A page that had to be exact would need more: for example, loading the list again after a push that arrived mid-load.

Two things that look alike

null means [] means
not loaded yet loaded, and there are none
a push leaves it as it is a push makes a list of one

That's why the page starts with null (topic 02), and why the handler has to check for it.
