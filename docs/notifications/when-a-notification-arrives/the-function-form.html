The Function Form

Give the setter a function instead of a value, and React calls it with the state as it is now. The handler no longer needs to see the list at all.

Here's what the app really does:

// Figure 5.16: adding a pushed notification
// (src/pages/NotificationsPage.jsx, excerpt)
// 2. Add each pushed notification to the top of the list.
useEffect(() => {
  function handleNotification(newNotification) {
    // This handler is registered once, when the page opens, so the
    // `notifications` variable it can see is the list as it was then
    // (null!). Passing setNotifications() a function instead lets React
    // hand it the list as it is *now*, and the function returns the new
    // list: the new notification, then all the current ones.
    setNotifications((currentNotifications) => {
      // Still loading: leave it. The API saved this notification before
      // pushing it, so the list on its way almost always includes it.
      // (Only if the API answered the list request in the moment before
      // the save is it missing, until the page is next opened.)
      if (currentNotifications === null) {
        return null;
      }
      return [newNotification, ...currentNotifications];
    });
  }

  const stopListening = onNotification(handleNotification);
  // Stop listening when the user leaves the page.
  return stopListening;
}, []);

Two ways to call a setter

You write React sets the state to
setNotifications(newList) newList, a value you worked out yourself
setNotifications((current) => newList) whatever your function returns, after React calls it with the current state

Every state setter accepts both. Until now the first was enough. The second is called the function form, or an updater function.

In the function form, the handler never reads notifications at all. It says how to change the list ("put this one in front"), and React supplies the list to change, as it is at that moment, not as it was when the handler was made.

When to use it

Use the function form when the new state is worked out from the old state, and the code that does it might run later than the render it came from:

  • a handler registered once, like this one, or a timer
  • code after an await, if the state could change while waiting (the next slide)

When neither is true, the plain form is fine, and it's what most of this app still uses. The function form would work there too, but the plain form is shorter and easier to read.

The null check is for a push that arrives before the list has loaded. The last slide of this topic is about it.
