Count Again, After the Save

Re-fetching the count picks up everything that changed, not just the push. It only works because the API saves the notification before it pushes it.

The provider's handler (Figure 5.15) is one line, loadUnreadCount(). Adding 1 to the count would have been one line too. Why ask the API?

Counting again catches more than the push

Asking the API gets the whole truth, every time:

  • Notifications that were never pushed. An SLA breach is saved by the worker, which has no socket (topic 01). Adding 1 per push would never count it. Counting again picks it up at the next push.
  • Changes made somewhere else. If Alex marks a notification read in another tab, this tab's count is out of date. The next push corrects it.
  • Nothing to get wrong. "Add 1" has to be right on every push, forever. "Ask the API" is right whenever it's asked.

The cost is one small request per push. A push only arrives when something happens to this user, so that's a handful of requests an hour, not one a second.

Why the new one is always in the answer

Re-fetching only works if the notification is already saved when the browser asks. The API makes sure of that, in notify.js:

// Database first: the realtime channel pushes the saved row, so it can't
// run until the row exists and has an id.

Lesson 8 made that choice so the push could carry the saved row, with its id ("Why the Database Goes First"). It also means the front-end can trust that whatever it hears about is already in the database.
