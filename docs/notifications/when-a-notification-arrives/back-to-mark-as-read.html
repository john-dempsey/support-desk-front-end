A Push While the List Is Loading →

Back to Mark as Read

handleMarkRead uses the list from the moment of the click. A push that lands while the PATCH is on its way would be lost, so it gets the function form too.

Topic 02's handleMarkRead (Figure 5.6) worked out the new list from notifications. In Part 1 that was safe: nothing else could change the list. Now a push can, and the await in the middle leaves room for one:

handleMarkRead was created in the render Alex clicked in, so its notifications is the list at the moment of the click. The push happened after that. When the PATCH answers, notifications.map(...) builds the new list from the old one, and notification 8 is dropped from the screen. It isn't lost for good (it's saved, so it's back the next time the page opens), but the screen and the count no longer agree.

The final code

So, now that pushes exist, handleMarkRead uses the function form too:

// Figure 5.17: marking one as read, the final version
// (src/pages/NotificationsPage.jsx, excerpt)
async function handleMarkRead(notificationToMark) {
  setMarkErrorMessage('');
  try {
    const updatedNotification = await markNotificationRead(
      notificationToMark.id,
    );
    // The API sends back the notification with readAt filled in. map()
    // makes a new array the same length, swapping in the updated one and
    // keeping every other notification as it was. It's the function form
    // again, because a push may have added to the list while this
    // request was on its way.
    setNotifications((currentNotifications) =>
      currentNotifications.map((notification) =>
        notification.id === updatedNotification.id
          ? updatedNotification
          : notification,
      ),
    );
    // One fewer unread, so NavBar's count needs updating too.
    refreshUnreadCount();
  } catch (error) {
    setMarkErrorMessage(error.message);
  }
}

(Reflowed to fit.) This is the stage-05 code. Compared with Figure 5.6, apart from the comment, only two things changed: (currentNotifications) => in front, and currentNotifications.map instead of notifications.map.

It's rare, and that's the point

The window is the few milliseconds a PATCH takes, so you're unlikely to see this happen by clicking. That's what makes it worth preventing in the code: a bug that happens once in a thousand clicks is very hard to find later.
