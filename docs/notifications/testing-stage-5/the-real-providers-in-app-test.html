The Real Providers in App.test

App.test.jsx's whole-visit test now runs the real NotificationsProvider too, so socket.js and the notifications API are faked, and onNotification has to return something.

Stage 4's last App.test.jsx test follows a whole visit through the real AuthProvider (Stage 4, topic 10). NavBar now needs useNotifications(), so that test needs the real NotificationsProvider as well:

// Figure 5.28: two real providers, and nothing that connects
// (src/App.test.jsx, excerpts)
vi.mock('./api/notifications.api.js');
// The real providers below would open a socket to the API, so it's faked.
vi.mock('./realtime/socket.js');

// ... in the whole-visit test:
getUnreadNotifications.mockResolvedValue([]);
// onNotification() returns a "stop listening" function.
onNotification.mockReturnValue(vi.fn());
render(
  <MemoryRouter initialEntries={['/login']}>
    <AuthProvider>
      <NotificationsProvider>
        <App />
      </NotificationsProvider>
    </AuthProvider>
  </MemoryRouter>,
);

The provider order is main.jsx's (topic 03): NotificationsProvider inside AuthProvider.

Real providers, fake edges

Everything React does here is real: logging in sets the user, the provider's effect runs, the count loads, logging out runs the cleanup. Only the edges are faked, where the app would reach outside itself: the API modules and the socket. That's the same line every test in this app draws.

Why mockReturnValue(vi.fn())?

A faked onNotification returns undefined. Most tests don't mind. But this test logs out, and logging out runs the provider's cleanup, which calls stopListening(). Calling undefined throws. So the test gives onNotification a function to return.

The other App.test.jsx tests use renderWithProviders, which has a fake notifications value, unreadCount 0 unless a test says otherwise. NavBar.test.jsx uses that option to check the link says "(3 unread)".
