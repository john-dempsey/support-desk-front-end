Notifications

Users see what the API has told them: a list of their notifications and an unread count, loaded over REST, then kept up to date live over Socket.IO.

  • What Stage 5 Adds

    Who this stage is for, why it uses two channels (REST and a socket), and which files change, before any of the code.

  • Loading Notifications and Marking Them Read

    The notifications API file, what a notification looks like, the page that loads the list, the component that shows it, and marking one as read with map().

  • The Unread Count, Shared

    A second context holds how many notifications are unread, loads it from the API whenever the user changes, and shows it in the navigation bar on every page.

  • Connecting a Socket

    One shared Socket.IO connection, opened when someone logs in: it tells the server whose it is on every connect, lets components listen for pushes, and closes on logout.

  • When a Notification Arrives

    A push from Casey's click to Alex's count, why the count is fetched again, and the function form of a state update, which a handler that's registered once needs.

  • Telling a Page It Changed

    When a notification is about the ticket on screen, the page says so and offers a Reload button, rather than reloading by itself and losing what the user was typing.

  • The Socket in DevTools

    Watching Socket.IO in the browser's Network tab: the requests that open it, the messages on the WebSocket, and what happens when the connection ends.

  • Testing Stage 5

    Testing code that waits for a server to speak first: a fake socket.io-client, a helper that pushes a notification in a test, and a test for each place that listens.

  • Making It Yours

    Tracing a push through Stage 5, then adding notifications, live over a socket, to your own case study's front-end.
