What a Notification Looks Like

Six fields: what happened (type), a sentence for the user (message), which ticket it's about, whether it's been read, and when it happened.

Here's part of Casey's answer to GET /notifications:

{
  "data": [
    {
      "id": 10,
      "type": "ticket.commented",
      "message": "Alex Agent commented on \"Cannot log in\".",
      "ticketId": 1,
      "readAt": null,
      "createdAt": "2026-10-20T07:22:15.781Z"
    },
    {
      "id": 5,
      "type": "ticket.commented",
      "message": "Admin Ada commented on \"Cannot log in\".",
      "ticketId": 1,
      "readAt": "2026-10-20T06:50:06.195Z",
      "createdAt": "2026-10-20T06:49:49.184Z"
    }
  ]
}

The first hasn't been read yet; the second has.

(Your ids, dates and list will be different.)

Each field

Field What it holds What the page does with it
id the notification's own ID the key, and the ID for marking it read
type what happened, e.g. ticket.commented nothing on this page (topic 06 uses it)
message a sentence written by the API, for people shows it as it is
ticketId the ticket it's about, or null once that ticket is deleted a View ticket link, when it isn't null
readAt null until it's read, then the time it was marked unread when it's null
createdAt when it happened, as an ISO string formatDate(), as for tickets

There's no isRead field: readAt is null or a date, and that's enough to tell. The front-end works it out with notification.readAt === null.

The five types

type Who's told
ticket.created the customer, and every agent
ticket.assigned the newly assigned agent
ticket.commented the customer, the assigned agent, and anyone watching the ticket with comment notifications on, but never whoever wrote the comment
ticket.status_changed the customer
ticket.sla_breached the assigned agent, or every admin if nobody is assigned

The API chooses who's told (Lesson 8, "One Listener Decides Who"). The front-end never decides who should know about what: it shows whatever comes back.

Try it

Log in to the app as Casey, open a ticket assigned to Alex, and add a comment. Then, in your REST client, send GET /notifications as Alex, then as Casey, then as Ada. Who got a new notification? Check it against the table.
