Three Requests About Notifications

notifications.api.js has one function per request: all of the user's notifications, only the unread ones, and marking one as read.

The new API file follows the same three steps as every other one: call apiRequest(), wait, return what's in data.

// Figure 5.2: listing notifications, and marking one as read
// (src/api/notifications.api.js, excerpt)
// GET /notifications: returns the user's notifications, newest first.
// Each is { id, type, message, ticketId, readAt, createdAt }; readAt is
// null until it's marked as read, and ticketId is null once its ticket has
// been deleted. There's no pagination, so no `meta`.
export async function getNotifications() {
  const responseBody = await apiRequest('/notifications');
  return responseBody.data;
}

// PATCH /notifications/:id/read: returns the notification, now with
// readAt set. There's no request body: the URL says it all.
export async function markNotificationRead(notificationId) {
  const responseBody = await apiRequest(
    `/notifications/${notificationId}/read`,
    { method: 'PATCH' },
  );
  return responseBody.data;
}

(The apiRequest() call in markNotificationRead() is reflowed to fit.)

The third function, getUnreadNotifications(), is the same as getNotifications() with ?unread=true on the end of the path. The navigation bar's count uses it (topic 03).

What each one sends and gets back

Function Sends Answer
getNotifications() GET /notifications 200 { data: [ … ] }, newest first
getUnreadNotifications() GET /notifications?unread=true the same, only those with readAt: null
markNotificationRead(id) PATCH /notifications/:id/read, no body 200 { data: { … } }, with readAt set

Only your own

There's no user ID anywhere in these requests. The API works out whose notifications to send from the token, exactly as it decides which tickets a customer sees. Another user's notification is a 404, as if it didn't exist (Lesson 7, "A User's Own Notifications").

A PATCH with no body

Every PATCH in Stage 3 sent a body: the fields to change. This one sends none, because there's only one thing it can change. The URL names it: /read. So markNotificationRead() passes apiRequest() a method and no body, and client.js sends no Content-Type header.

Try it

In your REST client, log in as Alex and send GET /notifications. Pick one notification's id. Then log in as Casey, and send PATCH /notifications/<that id>/read with Casey's token. What does the API answer, and why that status rather than 403?
