The Count Comes From the API

The provider never adds or subtracts: it asks the API for the unread list and counts it. A failure leaves the last number showing, because the count is extra information.

NotificationsProvider holds one piece of state, and one way to get it right:

// Figure 5.8: where the count comes from
// (src/context/NotificationsProvider.jsx, excerpt)
// The API is the truth: the count is always the length of the user's
// unread list, never a number this file adds to or takes away from.
async function fetchUnreadCount() {
  const unreadNotifications = await getUnreadNotifications();
  return unreadNotifications.length;
}

function NotificationsProvider({ children }) {
  const { user } = useAuth();
  const [unreadCount, setUnreadCount] = useState(0);

  // ... the effect that loads the count (next slide) ...

  // For pages that change what's unread, e.g. NotificationsPage after
  // "Mark as read".
  async function refreshUnreadCount() {
    try {
      const count = await fetchUnreadCount();
      setUnreadCount(count);
    } catch {
      // As above: keep the last number showing.
    }
  }

  const notificationsValue = { unreadCount, refreshUnreadCount };

  return (
    <NotificationsContext value={notificationsValue}>
      {children}
    </NotificationsContext>
  );
}

(The return is reflowed to fit.)

Count, don't calculate

After Mark as read, the page could have told the provider "take one away". It doesn't: it asks the provider to fetch the count again. One extra small request buys something worth having: every time the number changes, it's set to what the API says. Adding and taking away would need every change to be counted exactly once, forever; one missed or doubled step and the number would stay wrong until the next reload.

fetchUnreadCount() sits outside the component, because it uses nothing from inside it: no state, no props. It's an ordinary function, like formatDate().

A catch with nothing in it

Every page so far shows the user an error when a request fails. This catch deliberately shows nothing. Why the difference?

  • The count is extra information in the corner of every page. If the API is down, the page the user is looking at already says so, in its own error message. A second error in the navigation bar would say the same thing again, on every page.
  • Keeping the last number is a reasonable thing to show. It may be a little out of date; it isn't wrong.
  • One error still matters: a 401 means the session has ended. client.js handles that before the catch ever sees it, and logs the user out (Stage 4, topic 09).

The comment in Figure 5.8 says "As above", pointing at the same decision in the effect, where it's explained in full. An empty catch always deserves a comment saying why it's empty.
