render() and screen

render() adds a <div> to jsdom's page and has React draw the component into it, effects and all. screen searches the whole page, and screen.debug() prints it.

// Figure A.9: the loading state (src/pages/HomePage.test.jsx, excerpt)
it('shows a loading message while waiting for the API', () => {
  // A promise that never resolves keeps the page in its loading state.
  getWelcome.mockReturnValue(new Promise(() => {}));

  render(<HomePage />);

  expect(screen.getByRole('status')).toHaveTextContent(
    'Connecting to the API',
  );
});

(Stage 0's version. It's indented one level further in the file, and the last statement is one line there.)

render()

render(<HomePage />), from React Testing Library:

  1. creates a <div> and adds it to jsdom's document.body
  2. has React draw <HomePage /> into that <div>, the same job main.jsx does with the root element in the real app
  3. waits until React has finished, including running the component's effects, and only then returns

So by the next line, HomePage's effect has already called getWelcome(), and the page shows whatever it shows while it waits. (A throwaway test confirmed it: straight after render, getWelcome had been called once, and document.body held one <div>.)

This test's fake returns a promise that never settles, so the page stays in its loading state for as long as the test wants to look.

screen

screen is a set of queries (slides 03 and 04) that search all of document.body. Whatever render added is in there. screen.debug() prints what's there, which is the best way to find out why a query can't find something.

Try it

Add screen.debug(); straight after render(<HomePage />); in Figure A.9, and run npx vitest run src/pages -t loading. It prints:

<body>

    <p

      role="status"
    >
      Connecting to the API…
    </p>
  </div>
</body>

Find the <div> that render added, and the element that getByRole('status') found. Remove the line.
