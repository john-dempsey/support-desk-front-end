How a Query Finds an Element

getByRole works out every element's role and accessible name, as a screen reader does, and picks the one that matches. When none does, it lists what it found.

// Figure A.10: finding a heading (src/App.test.jsx, excerpt)
it('shows the not found page for an unknown URL', () => {
  renderAppAt('/no-such-page');

  expect(
    screen.getByRole('heading', { level: 1, name: 'Page not found' }),
  ).toBeInTheDocument();
});

(Stage 0's version. It's indented one level further in the file, and the expect is one line there. renderAppAt is a helper in the same file that renders the whole app at a URL: Figure 0.31, Stage 0, topic 08.)

Role and name

A screen reader doesn't see tags or classes. It sees what each element is (its role) and what it's called (its accessible name). getByRole works the same way. For each element on the page it works out:

  • the role, from the tag, unless a role attribute says otherwise:

    Element Role
    <h1> ... <h6> heading (with level 1 to 6)
    <a href="..."> link
    <button> button
    <nav> navigation
    <p role="status"> status

  • the name, usually the element's text, or its aria-label if it has one (<nav aria-label="Main"> is called "Main")

Then it keeps the elements whose role, name and other options (level) all match. This is why the queries double as an accessibility check (Stage 0, topic 07): if a test can't find a button by its role and name, a screen reader user probably can't either.

When nothing matches

The error lists every role it did find, with each element's name. That list usually shows the mistake at once: a typo in the name, a <div> where a <button> should be, or a missing label.
