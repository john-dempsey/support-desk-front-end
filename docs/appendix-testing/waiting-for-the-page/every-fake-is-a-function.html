Every Fake Is a Function Underneath

mockResolvedValue and the rest are shortcuts for mockImplementation, which gives the fake a whole function to run. That function sees the arguments, so it can answer differently for each.

Each mock...Value method from topic 04 is a shortcut. Underneath, a vi.fn() fake runs a function each time it's called, and these methods give it a simple one:

Shortcut The function it gives the fake
mockReturnValue(x) () => x
mockResolvedValue(x) () => Promise.resolve(x)
mockRejectedValue(error) () => Promise.reject(error)
mockImplementation(fn) fn itself

mockImplementation is the general one. Your function gets the same arguments the fake was called with, so it can decide what to answer. Figure 2.22 (Stage 2, topic 07) uses it to make getTicket fail for one ID and succeed for another:

getTicket.mockImplementation(async (ticketId) => {
  if (ticketId === '999') {
    throw createApiError(404, 'Ticket 999 not found');
  }
  return unassignedTicket;
});

Because the function is async, return gives a resolved promise and throw gives a rejected one: the same two answers as the shortcuts.

A pretend error with a status

The page decides what to show from error.status, so the fake has to throw the same kind of error apiRequest() does. The test file has its own small copy of client.js's helper:

// Figure A.16: a pretend API error (src/pages/TicketDetailPage.test.jsx,
// excerpt)
function createApiError(status, message) {
  const error = new Error(message);
  error.status = status;
  return error;
}

A fake only has to be realistic in the ways the code under test looks at. The page reads status and message, so that's all this error has.
