What userEvent Fires

userEvent.type() doesn't set the input's value. It clicks the input, then presses each key, firing the same events a browser would, and waits for React after each one.

Stage 3's tests type and choose with user-event (Figure 3.58, Stage 3, topic 10). To see what one call really does, a throwaway test listened for every event on a plain <input> while running await userEvent.type(input, 'ab'):

pointerdown mousedown focus pointerup mouseup click
keydown() keypress() beforeinput() input(a) keyup(a)
keydown(a) keypress(a) beforeinput(a) input(ab) keyup(ab)

(The brackets show the input's value when each event fired. The output is one line in the terminal.)

  • First, a click. A user can't type into a field without clicking it, so user-event clicks first, and the input gets the focus.
  • Then each key in turn: keydown, keypress, beforeinput, input, keyup. The value grows by one letter at the input event. React's onChange listens for input, so a controlled input's onChange runs once per letter, as it does in a browser.

Why not just set the value?

Testing Library also has fireEvent, which fires one event of your choice. fireEvent.change(input, { target: { value: 'ab' } }) would set the value in one go. The app's tests never use it, because no user types like that. user-event behaves like a person, so it also can't do what a person can't: clicking a disabled button does nothing (a throwaway test's onClick fake recorded no calls).

Why every call is awaited

Between events, user-event waits for React to finish drawing, so the next event sees the up-to-date page. That waiting takes time, so every call returns a promise, and the test has to await it.

The app calls userEvent.type(...) and userEvent.click(...) directly. user-event's documentation also shows const user = userEvent.setup() followed by user.type(...). The direct calls do the same thing, starting a fresh "user" for each call.
