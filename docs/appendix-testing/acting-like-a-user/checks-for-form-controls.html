Checks for Form Controls

jest-dom has checks for what a form control holds and how a screen reader describes it. toHaveAccessibleDescription follows aria-describedby to the error message.

Stage 3's forms brought five more jest-dom matchers:

Matcher Passes when the element ...
toHaveValue('...') is an input, text area or select holding this value
toHaveDisplayValue('...') shows this text: for a <select>, the chosen option's text, not its value
toBeDisabled() / toBeEnabled() can't / can be used (e.g. a button while saving)
toHaveAccessibleDescription('...') is described by this text, for a screen reader
toHaveAttribute('aria-invalid', 'true') has this attribute, with this value (from Stage 1)

What "accessible description" means

A field's name comes from its <label>. Its description is any extra text a screen reader reads after the name. TicketForm gives the subject input aria-describedby="ticket-subject-error" when there's an error, which points at the error message's id. A screen reader then reads "Subject, subject is required".

// Figure A.21: an error a screen reader can find
// (src/pages/NewTicketPage.test.jsx, excerpt)
expect(await screen.findByText('subject is required')).toBeInTheDocument();
expect(screen.getByLabelText('Subject')).toHaveAttribute(
  'aria-invalid', 'true',
);
expect(screen.getByLabelText('Subject')).toHaveAccessibleDescription(
  'subject is required',
);

(Stage 3's version, from the validation test. The last two expects are one line each in the file, split here to fit.)

toHaveAccessibleDescription does what the screen reader does: it reads aria-describedby, finds the element with that id, and takes its text. The first expect only proves the message is somewhere on the page. This one proves it's joined to the right field.
