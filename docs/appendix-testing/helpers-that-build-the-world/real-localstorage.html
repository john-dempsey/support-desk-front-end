Real localStorage, Shared by a File's Tests

jsdom's localStorage really stores things, and it lasts until the file's process ends. So setup.js clears it after every test, or a saved token leaks into the next one.

Stage 4 saves the token in localStorage (Stage 4, topic 02). The tests don't fake it: jsdom's localStorage is a real one, just kept in memory instead of on disk. AuthProvider.test.jsx uses it as the app does, with saveToken('saved-token') before rendering.

How long it lasts

Like everything else in a test file's world (topic 01), localStorage belongs to the file's process:

  • between files, nothing is shared: each file starts with an empty one
  • between tests in the same file, it's shared: whatever one test saves is still there for the next

So setup.js gained a line in Stage 4:

// Figure A.24: every test starts logged out (src/test/setup.js, excerpt)
afterEach(() => {
  cleanup();
  localStorage.clear();
});

(Stage 4's version.)

It's the same kind of tidying as cleanup() (topic 03), for a different leftover.

Try it

In setup.js, put // in front of localStorage.clear(); and run npm test. Three tests fail:

 FAIL  src/api/client.test.js > apiRequest > doesn't call the handler
for a 401 with no token, e.g. a wrong password
 FAIL  src/context/AuthProvider.test.jsx > AuthProvider > logout()
forgets the token and logs the user out
 FAIL  src/context/AuthProvider.test.jsx > AuthProvider > logs the user
out when any later request gets a 401

(Each is one line in the terminal.) Take the first: the test before it in client.test.js saved 'expired-token'. What did this test expect, and what did the leftover token change? Then run npx vitest run --sequence.shuffle a few times, still without the clear. Do the same three tests fail each time? Remove the //.
