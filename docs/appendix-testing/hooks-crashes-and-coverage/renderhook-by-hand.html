renderHook(), by Hand

A hook can only run inside a component, so renderHook() makes one: a component that calls the hook, saves what it returns in result.current, and draws nothing.

useFetch is a hook, and React only lets a hook run inside a component. To test it on its own, Stage 6 uses renderHook():

// Figure A.28: running a hook (src/hooks/useFetch.test.js, excerpt)
const fetchTickets = vi.fn().mockResolvedValue(['first ticket']);

const { result } = renderHook(() =>
  useFetch(fetchTickets, 'status=open'),
);

expect(result.current.isLoading).toBe(true);

(Stage 6's version, the start of the first test. The renderHook call is one line in the file, split here to fit.)

The same thing, by hand

renderHook saves you writing this:

function renderMyHook(useTheHook) {
  const result = { current: null };

  function TestComponent() {
    result.current = useTheHook();
    return null;
  }

  render(<TestComponent />);
  return { result };
}
  • TestComponent is a component, so the hook is allowed to run in it. It draws nothing (return null): the hook's return value is all the test wants.
  • Every time it renders, it saves the hook's latest return value in result.current. When the fake answers and the hook's state changes, React renders TestComponent again, and result.current is updated.
  • That's why the test reads result.current.isLoading each time, rather than saving result.current in a variable once: the variable would keep the first render's value.

renderHook also returns rerender, which renders TestComponent again with new props, as topic 10's did for a component. Stage 6's "ignores a slow answer" test (Figure 6.8) uses it to change the ticket ID.
