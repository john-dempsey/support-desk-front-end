What waitFor() Needs From Its Check

waitFor() runs its check again and again until it stops throwing. A check that returns false instead of throwing counts as passed at once.

findBy... waits for an element. waitFor waits for any check. It's the general tool underneath: findByText('x') is waitFor(() => getByText('x')) (topic 05).

await waitFor(() => expect(result.current.isLoading).toBe(false));

waitFor(check) calls check straight away, then again every 50 ms and whenever the page changes (the same rules as findBy):

  • if check throws, that try failed: try again later
  • if check doesn't throw, waitFor finishes
  • after 1000 ms of throwing, waitFor fails with the last error

So the check must throw when it's not ready, and an expect is the easy way to do that.

The mistake that waits for nothing

This looks right, but isn't:

await waitFor(() => result.current.isLoading === false);

The arrow function returns false while loading, but it doesn't throw. To waitFor, not throwing means "done", so it finishes at once, before the fake has answered.

Try it

In useFetch.test.js's first test, change the waitFor line to the mistaken one above and run npx vitest run src/hooks -t "is loading at first":

AssertionError: expected null to deeply equal [ 'first ticket' ]

The waitFor line passed. The next line failed, because the data hadn't arrived. When a test fails just after a waitFor, check the waitFor first. Now delete the waitFor line altogether: which line fails now? Put it back.
