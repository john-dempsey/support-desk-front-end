within(): Queries Tied to an Element

Every query searches inside some element. screen's queries search document.body; within(element) gives the same queries, searching inside that element instead.

Every query function takes two things: where to search, and what to look for. Writing the "where" every time would be tedious, so Testing Library gives you sets of queries with it already filled in:

You write Searches inside
screen.getByText(...) document.body: the whole page
within(element).getByText(...) only element

That's all within() does. It's not a special kind of search: it's the same queries as screen, tied to a different element. In fact within(document.body) gives exactly what screen gives.

// Figure A.13: inside one row (src/components/TicketList.test.jsx, excerpt)
const mouseRow = screen.getByRole('row', { name: /Mouse missing/ });
expect(within(mouseRow).getByText('Unassigned')).toBeInTheDocument();

The first line finds the row on the whole page. The second searches only that row. Without within, the test would pass even if "Unassigned" were printed in the wrong row.

Queries from render()

render() returns a set of queries too, tied to the <div> it created (topic 05). You'll see const { getByText } = render(...) in other projects' tests. The app always uses screen instead, so tests read the same whether they render one component or the whole app.

Try it

TicketList's heading row is the first row, and its cells are columnheaders. Add a test that counts them:

const headingRow = screen.getAllByRole('row')[0];
expect(within(headingRow).getAllByRole('columnheader')).toHaveLength(5);

Does it pass? Now replace within(headingRow) with screen. Does it still pass, and why? (How many column headers are on the whole page?)
