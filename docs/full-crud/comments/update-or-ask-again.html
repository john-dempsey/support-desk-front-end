Update, or Ask Again?

After a change, a page can update the state it has from the response, or ask the API again. The edit page asks again; the comments update. Here's how to choose.

Every change in this lesson ends with the page showing the result. There have been two ways of doing that:

Ask the API again Update the state you have
Where creating, editing and deleting a ticket adding and deleting a comment
How navigate() to a page that loads fresh setComments(...) with a new array
Requests one more GET none
Shows exactly what the database has what the page worked out the database has

When updating is safe

The comments can be updated in place because the page knows exactly what changed, and where:

  • adding: the API sends back the whole saved comment, author included, and comments are sorted oldest first, so a new one always goes at the end
  • deleting: a 204 means it's gone, so the list is the old one without it

So the result is the same as asking again, without the wait or the extra request. That matters on a page the user stays on, adding comment after comment.

When to ask again

Asking again is simpler and always right. Choose it when the page can't easily work out the result itself:

  • the API decides something the page can't predict, such as the order of a sorted list (you'll meet one later in this lesson)
  • the change affects things the response doesn't include
  • the page is leaving anyway, as after saving a ticket: the next page loads fresh at no extra cost

Neither shows other people's changes

If Alex adds a comment while you're looking at the ticket, you won't see it either way, until you reload the page. Showing other people's changes as they happen is what Stage 5's notifications are for.
