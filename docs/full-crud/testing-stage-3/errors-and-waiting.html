Errors, and Waiting

The fake API can fail on purpose, with a status and details, so the tests can check each message lands in the right place. A promise that never answers holds the page mid-request.

A 400, with details

// Figure 3.62: details by the field
// (src/pages/NewTicketPage.test.jsx, excerpt)
const validationError = new Error('Validation failed');
validationError.status = 400;
validationError.details = [
  { field: 'subject', message: 'subject is required' },
];
createTicket.mockRejectedValue(validationError);
renderNewTicketPage();

await fillInAndSubmit('   ', 'Paper stuck');

expect(await screen.findByText('subject is required')).toBeInTheDocument();
expect(screen.getByLabelText('Subject')).toHaveAttribute(
  'aria-invalid', 'true',
);
expect(screen.getByLabelText('Subject')).toHaveAccessibleDescription(
  'subject is required',
);
expect(screen.getByLabelText('Description')).toHaveAttribute(
  'aria-invalid', 'false',
);

(A comment is left out, and the details and the last three lines are each one line in the file, split here to fit.)

The fake error is built the same way apiRequest() builds a real one (Stage 0, topic 05), so the page can't tell the difference.

  • toHaveAccessibleDescription() checks what a screen reader reads after the label. It passes only if aria-describedby points at the right FieldError (topic 04, slide 04). This one line tests the accessibility wiring.
  • The description has aria-invalid="false": the error went to the right field, and only that one.

The test types three spaces, as a user would to get past required. (In jsdom, required doesn't stop a form being submitted at all, so a test can't check the browser's own validation. It checks the API's.)

Any other error

A 403 has no details, so the test only checks the message:

expect(await screen.findByRole('alert'))
  .toHaveTextContent('You do not have permission');

Waiting forever

How do you test what the button looks like while the request is on its way? Give the fake a promise that never settles:

createTicket.mockReturnValue(new Promise(() => {}));
// ... fill in and submit
expect(screen.getByRole('button', { name: 'Saving…' })).toBeDisabled();

Stage 2 used the same trick to test "Loading…". The page waits for an answer that never comes, so it stays mid-request, and the test can look at it.
