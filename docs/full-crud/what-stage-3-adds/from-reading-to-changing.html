From Reading to Changing

Stage 2 could only read tickets. Stage 3 creates, edits and deletes them, and adds comments, tags, and a way to find tickets in a long list.

At the end of Stage 2, the app could read: a list of tickets, and one ticket at a time. Every request it sent was a GET.

The back-end could do more than that from Lesson 3, "Full CRUD REST API": it can create, update and delete tickets, comments and tags. Stage 3 is the front-end's Lesson 3. It gives each of those a page, a form or a button, so the front-end can do everything CRUD stands for:

Stage 2 Stage 3
Create a ticket, a comment, a tag
Read the list, one ticket the same, plus comments, tags and agents
Update a ticket (including its status and agent), a tag's name
Delete a ticket, a comment, a tag

The pages, and how they connect

Two kinds of arrow:

  • a solid arrow is a link the user clicks, like every link so far
  • a dashed arrow is new: after a change is saved, the page moves the user on by itself. After creating a ticket you see it; after deleting one, you're back at the list. Topic 03 shows how.

Try it

With the API running and npm run dev started, open each URL in the diagram, using ticket 2 for :ticketId. Then click Tags in the navigation bar. Don't change anything yet: just find each page, and match it to its box.

If every page says Invalid or expired token, your token from Stage 2 has run out: tokens last one day. Log in again in your REST client, and paste the new token into .env (Stage 2, topic 02, "A Token Is Not a Setting"). You'll need to do this each day you work on the app, until Stage 4 adds a login page.
