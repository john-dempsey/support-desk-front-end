Every Control, for Now

Stage 3 shows every button and form to everyone. Ada's admin token is allowed to use all but one of them, and the API says no to that one.

In the back-end, Lesson 4 decided who may do what, with authorize(...) on each route. Lesson 7's GET /users follows the same rule:

Request Who the API allows
POST /tickets customers only
PATCH /tickets/:id, DELETE /tickets/:id agents and admins
POST, PATCH, DELETE on /tags agents and admins
GET /users?role=agent agents and admins
comments anyone who can see the ticket. Only the author (or an admin) may delete one

The front-end has no login yet, so it doesn't know who's using it. Every request carries the stand-in token from .env, which is Ada's, and Ada is an admin.

So Stage 3 shows every control to everyone: the New ticket link, Edit, Delete, the status and agent dropdowns, and the Tags page. There are no role checks anywhere in this stage's code.

The one thing Ada can't do

Look down the table: an admin may do everything except create a ticket, which is for customers. With Ada's token, the New ticket form gets a 403, and shows the API's message:

You do not have permission to perform this action

That's not a bug in the front-end. It's the API protecting itself, as Lesson 4 designed it to. Topic 03 shows how to switch to a customer's token to create a ticket.

Hiding is not protecting

Stage 4 adds a login, and then hides each control from the roles that can't use it: no New ticket link for an agent, no Edit or Delete for a customer. That makes the app easier to use, because nobody is shown a button that can only fail.

It doesn't make anything safer. Anyone can send a request with a REST client, and skip the front-end entirely. The API checks every request itself, so it stays the only real guard. A front-end that relies on hiding buttons for security has no security.

If your API has no authentication

Everything in this stage still works. With VITE_DEV_TOKEN empty, no token is sent, your API allows every request, and there's no 403 to see. Nothing in Stage 3 depends on a login, a role or a token.

Try it

In your REST client, log in as casey@example.com and send PATCH /tickets/1 with Casey's token and the body { "status": "resolved" }. What status comes back, and which line of the back-end's ticket.routes.js sent it? (The API allows only 10 logins every 15 minutes. If you get a 429, wait a few minutes.)
