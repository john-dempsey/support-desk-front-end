Changing the URL

Choosing a filter or a page makes a new copy of the query, changes it, and hands it to setSearchParams(). The URL changes, and the effect does the rest.

When the user chooses a status, the page doesn't load anything itself. It only changes the URL:

// Figure 3.55: changing the query (src/pages/TicketListPage.jsx,
// excerpt)
function handleFilterChange(name, value) {
  const newSearchParams = new URLSearchParams(searchParams);
  if (value) {
    newSearchParams.set(name, value);
  } else {
    newSearchParams.delete(name);
  }
  newSearchParams.delete('page');
  setSearchParams(newSearchParams);
}

function handlePageChange(newPage) {
  const newSearchParams = new URLSearchParams(searchParams);
  newSearchParams.set('page', newPage);
  setSearchParams(newSearchParams);
}

(The comments are left out.)

Then the loop from the previous slide takes over: the URL changes, queryString changes, and the effect loads the matching tickets.

A copy, not the original

new URLSearchParams(searchParams) makes a copy of the current query. The page changes the copy, and hands it to setSearchParams(). It's the rule from topic 07: never change what React gave you; make a new one.

set() and delete()

  • set(name, value) adds the parameter, or replaces it if it's there already: status=open becomes status=closed.
  • delete(name) takes it out. Choosing All statuses sends '', so status is removed, and the API uses its default: every status.

Back to page 1

delete('page') runs for every filter or sort change. Say you're on page 3 of every ticket, and choose Open: there might only be one page of open tickets, so "page 3" would be empty. Starting again from page 1 makes sense to a user, too.

handlePageChange changes only page, and keeps everything else, so the filter and order stay as they are while you move through the pages.

The Back button

By default, setSearchParams() adds a new entry to the browser's history, just like clicking a link. So every choice can be undone with Back, one at a time.
