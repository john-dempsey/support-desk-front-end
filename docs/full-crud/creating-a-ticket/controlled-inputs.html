Controlled Inputs

Each input shows a piece of state, and typing updates the state. React, not the input, holds the value.

In a Blade form, the browser keeps what you type inside the input. Nothing reads it until the form is posted, and then Laravel finds it in $request->input('subject').

A React form usually works the other way round. Each input's value lives in state, and the input just shows it:

// Figure 3.8: the subject input (src/components/TicketForm.jsx, excerpt)
const [subject, setSubject] = useState(initialValues.subject);
// ...
<input
  id="ticket-subject"
  type="text"
  required
  maxLength={200}
  value={subject}
  onChange={(event) => setSubject(event.target.value)}
/>

(Two more lines in the <input>, starting with aria-, are left out here. Topic 04 explains them.)

This is called a controlled input: React controls what it shows.

One keypress

Two props make it work:

  • value={subject} says "show whatever is in subject". Not what was typed: what's in state.
  • onChange runs on every keypress. event.target is the input, and event.target.value is what it would now show, with the new character. setSubject() saves that into state.

So typing a "P" goes round a small loop:

  1. The user presses P. onChange runs.
  2. setSubject('P') changes the state.
  3. React re-renders TicketForm, and value={subject} now shows "P".

It all happens in a few milliseconds, so it looks the same as a normal input. The difference is that the current value is always in a variable, ready to send, check or show somewhere else.

initialValues.subject is the value the state starts with. For a new ticket, it's '', an empty string. Topic 05 starts it with an existing ticket's subject instead.

One state per input

The description <textarea> works the same way, with its own description state and setDescription(). In JSX, a <textarea> takes value like an <input>, not text between its tags as in HTML.
