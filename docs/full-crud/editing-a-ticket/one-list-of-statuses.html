One List of Statuses

The status words used to live in StatusBadge. Now three files need them, so they move to their own file in utils/.

In Stage 1, StatusBadge held the words for each status, in a STATUS_LABELS object at the top of the file. It was the only file that needed them.

Stage 3 has two more: the status dropdown in TicketForm, and the status filter on the list page (topic 09). Copying the object into each would work, until someone changed "In progress" to "Being worked on" in one file and forgot the others.

So the list moves to its own file:

// Figure 3.28: every status, once (src/utils/ticketStatuses.js)
// In the order they're shown in a dropdown.
export const TICKET_STATUSES = [
  'open', 'in_progress', 'resolved', 'closed',
];

export const STATUS_LABELS = {
  open: 'Open',
  in_progress: 'In progress',
  resolved: 'Resolved',
  closed: 'Closed',
};

(The comment at the top of the file is left out, and TICKET_STATUSES is split here to fit. It's one line in the file.)

  • TICKET_STATUSES is the list to loop over, in order. A dropdown should always list the statuses in the same, sensible order: the order a ticket moves through them.
  • STATUS_LABELS looks up the words for one status, as StatusBadge always did.

Why two? An object's keys can be looped over, but an array says plainly "this is the order". The dropdowns map() over the array and look up each label in the object (Figure 3.25).

StatusBadge imports it

StatusBadge loses its own copy, and imports the shared one instead:

// Figure 3.29: the change to StatusBadge (src/components/StatusBadge.jsx,
// excerpt)
import styles from './StatusBadge.module.css';
import { STATUS_LABELS } from '../utils/ticketStatuses.js';

Nothing else in StatusBadge changes, and it looks exactly the same on screen. Changing how code is organised without changing what it does is called refactoring. The tests from Stage 1 prove it worked: they still pass, untouched.

The back-end has the same list, as statusEnum in ticket.validators.js, and its comment says it's kept in step with the Prisma schema by hand. The front-end's list has to be kept in step with the API's by hand too. If the API ever added a status, this is the one front-end file to change.

Try it

Change 'In progress' to 'Being worked on' in ticketStatuses.js. Where does the new wording appear? Run npm test: which tests fail, and why is that a good thing? Put it back.
