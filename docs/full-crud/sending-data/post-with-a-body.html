POST, with a Body

createTicket() is getTicket() with two more things: a method, and a body for apiRequest() to send as JSON.

Every function in tickets.api.js so far has sent a GET. Here's the first that sends data:

// Figure 3.3: creating a ticket (src/api/tickets.api.js, excerpt)
// POST /tickets: `newTicket` is { subject, description }. Returns the
// saved ticket, including the id the database gave it.
export async function createTicket(newTicket) {
  const responseBody = await apiRequest('/tickets', {
    method: 'POST',
    body: newTicket,
  });
  return responseBody.data;
}

(The apiRequest() call is on one line in the file. It's split here to fit.)

Put it next to getTicket() from Figure 2.5. The only difference is the second argument to apiRequest(), the options object:

  • method: 'POST'. Without it, apiRequest() sends a GET.
  • body: newTicket. A plain JavaScript object, such as { subject: 'Printer jammed', description: 'Paper stuck in tray 2' }.

That's all createTicket() has to do. Stage 0's apiRequest() already knows what to do with a body (Figure 0.14): turn it into JSON text with JSON.stringify(), and add the Content-Type: application/json header so the back-end's express.json() can read it into req.body.

What comes back

The back-end's createTicket controller answers 201 Created, with the saved ticket in data:

{
  "data": {
    "id": 5,
    "subject": "Printer jammed",
    "description": "Paper stuck in tray 2",
    "status": "open",
    "customer": { "id": ..., "name": "Casey Customer", "email": "..." },
    "createdAt": "2026-10-15T09:30:00.000Z"
  }
}

(Shortened: some fields are left out. Your ids will be different.)

201 is a 2xx status, so response.ok is true, and apiRequest() treats it like a 200. createTicket() returns the ticket in data.

The most useful part of it is the id. The browser didn't know it: the database chose it. With the id, the page can go straight to the new ticket's own page, /tickets/5. That's the dashed "saved" arrow from New ticket in the diagram in topic 01.

The front-end never sends customerId

newTicket has only subject and description. Who the ticket belongs to comes from the token, not the body: the back-end reads req.user.id (Lesson 4). The back-end's createTicketSchema doesn't even accept a customerId, so a customer can't create a ticket in someone else's name.
