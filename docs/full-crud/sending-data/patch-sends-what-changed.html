PATCH Sends What Changed

updateTicket() takes the ticket's id and an object of changes. PATCH means the API changes only the fields it's sent.

// Figure 3.4: changing a ticket (src/api/tickets.api.js, excerpt)
// PATCH /tickets/:id: `changes` holds only the fields to change, e.g.
// { status: 'resolved' }. Returns the ticket as it is now.
export async function updateTicket(ticketId, changes) {
  const responseBody = await apiRequest(`/tickets/${ticketId}`, {
    method: 'PATCH',
    body: changes,
  });
  return responseBody.data;
}

Two arguments this time:

  • ticketId goes in the URL, which says which ticket.
  • changes goes in the body, which says what to change.

It's the same split as the back-end's route: req.params.id for which ticket, req.body for the new values.

PATCH, not PUT

PATCH means "change only these fields, and leave the rest as they are". The back-end's updateTicketSchema makes every field optional, and needs at least one. So all of these are valid:

updateTicket(2, { status: 'resolved' });
updateTicket(2, { assignedAgentId: 3 });
updateTicket(2, { assignedAgentId: null }); // unassign it
updateTicket(2, { subject: 'Charged twice', status: 'in_progress' });

PUT would mean "replace the whole ticket with this", so every request would have to send every field. With PATCH, a page can send only what it has.

What comes back

The API answers 200 with the whole ticket as it is now, after the change, including customer and assignedAgent. updateTicket() returns it, so a page could use it straight away. Topic 05 explains why the edit page doesn't need to.

The pattern

createTicket() and updateTicket() have the same three steps as every function in the file, and as getWelcome() in Stage 0:

  1. call apiRequest() with a path, and options if it's not a GET
  2. wait for it
  3. return what's in data
