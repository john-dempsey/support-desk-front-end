Showing It Under the Field

FieldError shows the message, and two aria attributes link it to its input, so a screen reader reads it out and the input is marked as having a problem.

The message is shown by a small new component:

// Figure 3.19: one field's error (src/components/FieldError.jsx)
function FieldError({ id, message }) {
  if (!message) {
    return null;
  }

  return (
    <p id={id} className="field-error">
      {message}
    </p>
  );
}

(The comment at the top is left out.)

When message is '', it returns null, which React shows as nothing. Otherwise, a paragraph with the message, and an id.

Linking it to the input

Seeing a message under a box is enough for most users. A screen reader user moving through the form needs to hear it, at the moment they reach the input. Two attributes do that:

// Figure 3.20: the subject input, in full (src/components/TicketForm.jsx,
// excerpt)
<input
  id="ticket-subject"
  type="text"
  required
  maxLength={200}
  value={subject}
  onChange={(event) => setSubject(event.target.value)}
  aria-invalid={Boolean(subjectError)}
  aria-describedby={
    subjectError ? 'ticket-subject-error' : undefined
  }
/>
<FieldError id="ticket-subject-error" message={subjectError} />

(The aria-describedby line is one line in the file. It's split here to fit.)

  • aria-invalid tells assistive technology the value has a problem. Boolean('') is false and Boolean('subject is required') is true, so it's "true" only when there's a message.
  • aria-describedby names the id of the element that describes the input. When the user reaches Subject, a screen reader reads its label, then the message, something like "Subject, invalid entry, subject is required" (each screen reader words it a little differently). When there's no message, the value is undefined, and React leaves the attribute out altogether, so it never points at an element that isn't there.

The id on FieldError and the value of aria-describedby must match exactly. The description textarea does the same, with ticket-description-error.

Not by colour alone

/* Figure 3.21: a field with a problem (src/index.css, excerpt) */
[aria-invalid='true'] {
  border: 2px solid var(--colour-error-text);
}

The CSS uses the same aria-invalid attribute to give the input a thicker, red border. The border isn't the only sign, though: the message is there in words. Someone who can't tell red from grey still knows what's wrong (Stage 0, topic 07).
