Two Sets of Rules

The browser checks the form before it's sent, using the same rules as the back-end's Zod schema. But only the API's check counts.

The back-end's createTicketSchema (Lesson 3) has the rules for a new ticket. The form's inputs repeat the simple ones as HTML attributes:

Field The API's rule (Zod) The browser's rule (HTML)
subject .trim().min(1): not empty, ignoring spaces required
subject .max(200) maxLength={200}
description .trim().min(1) required

The browser checks first

With required, the browser won't send the form while the field is empty. It shows its own message next to the input (the wording depends on the browser and its language), and handleSubmit never runs. maxLength stops the user typing a 201st character at all.

So the most common mistakes are caught instantly, without a request to the API. That's the reason to repeat the rules: it's quicker and friendlier for the user.

The API has the final say

The browser's checks are a convenience, not protection:

  • They're not the same rules. required is happy with three spaces. Zod trims them off first, finds nothing left, and says no.
  • They can be skipped. Anyone can send a request with a REST client, or remove required in the browser's developer tools. The API checks every request, wherever it came from.
  • Some rules can only be checked by the API. A tag name that's already taken (topic 08) needs the database to know.

So the front-end must always be ready for the API to say no, and show its reasons. That's the rest of this topic.
