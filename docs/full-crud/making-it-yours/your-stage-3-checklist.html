Your Stage 3 Checklist

The same steps for your own case study: create, edit and delete forms, validation errors by the field, related records, and a list you can filter and page.

At the end of Stage 2, your own front-end loaded its list and detail pages from your API. Here's how to change the data too, in the order this lesson did it. The examples use a booking system; swap in your own entity.

Run npm test and try the page in the browser after every step, and commit when both work. Not every step will fit your API: skip the ones it has no endpoints for.

1. The API module

Add createBooking(), updateBooking() and deleteBooking() to bookings.api.js (Figures 3.3 to 3.5). Check your back-end's routes for each one's method and body.

2. Create

  • BookingForm.jsx: one piece of state per field, controlled inputs with labels, and onSubmit and submitLabel props (Figures 3.8 to 3.11). Copy the browser checks (required, maxLength, type) from your Zod schema.
  • NewBookingPage.jsx at /bookings/new: handleCreate with navigate() to the new booking (Figure 3.12).
  • A link to it from the list page.

3. Validation errors

Copy getFieldError.js and FieldError.jsx as they are: they work with any API that uses this error shape. Keep the whole error in the page, and give each input aria-invalid and aria-describedby (Figures 3.15 to 3.20). Then send something your schema rejects, and check each message appears under its own field.

4. Edit

EditBookingPage.jsx at /bookings/:bookingId/edit: load the booking (and anything a dropdown needs, with Promise.all()), build initialValues, reuse BookingForm, and save with PATCH (Figures 3.22 to 3.30). Watch for dropdowns of ids: strings in the form, numbers or null for the API.

5. Delete

A Delete button on the detail page, with window.confirm(), and navigate() back to the list (Figures 3.31 to 3.33). Find out what your API answers when a record can't be deleted, and show it.

6. Related records, and simple ones

  • If your API nests one resource under another (like comments), add a list and a form to the parent's page, with the state in the page (topic 07).
  • If it has a simple resource (like tags), give it one page with all four operations (topic 08).

7. Filter, sort and page

If your list endpoint takes query parameters, add useSearchParams(), pass the query string straight through, and add Pagination (topic 09). If it doesn't, skip this step.

8. Tests

  • A test per API function (Figure 2.17's pattern).
  • For each form page: what's sent, where it goes, a 400 with details, and the disabled button (topic 10).
  • For each delete: OK and Cancel, with vi.spyOn(window, 'confirm').
  • Add the new routes to App.test.jsx, and fake every API module the pages use.

If your API has no authentication

Every step works the same. You won't see any 403s, and there's no token to switch. Nothing in this stage needs a login.
