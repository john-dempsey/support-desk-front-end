Asking Again for a Sorted List

The API sorts tags by name, so a new or renamed tag could belong anywhere in the list. The page asks the API for the list again, instead of working out where.

Comments are easy to add to the list the page has: a new comment always goes at the end (topic 07). Tags are different. The API returns them sorted by name, so a new tag could belong anywhere:

The page could sort the list itself. But the API already does, and its idea of alphabetical order (from the database) might not match JavaScript's in every case. So the page asks the API again, the other way from topic 07, slide 08:

// Figure 3.47: adding, then asking again (src/pages/TagsPage.jsx,
// excerpt)
async function reloadTags() {
  const latestTags = await getTags();
  setTags(latestTags);
}

async function handleAddTag(name) {
  setAddError(null);
  try {
    await createTag(name);
    await reloadTags();
    return true;
  } catch (error) {
    setAddError(describeTagError(error));
    return false;
  }
}

(The comments are left out. describeTagError is slide 06.)

createTag() returns the saved tag, but the page doesn't use it: reloadTags() gets the whole list again, in the right order, with the new tag in it. reloadTags is a separate function because renaming needs exactly the same thing.

Renaming

// Figure 3.48: renaming (src/pages/TagsPage.jsx, excerpt)
async function handleRenameTag(name) {
  setRenameError(null);
  try {
    await updateTag(editingTagId, name);
    await reloadTags();
    setEditingTagId(null);
    return true;
  } catch (error) {
    setRenameError(describeTagError(error));
    return false;
  }
}

Renaming "billing" to "invoices" moves it down the list, so the page asks again here too. Then setEditingTagId(null) puts the row back to showing its (new) name. The id comes from editingTagId: the form doesn't need to know which tag it's renaming.

One thing to notice

If createTag() works but reloadTags() fails (the API stops in between, say), the catch shows an error, although the tag was saved. It's rare, and a reload shows the truth, but it's the cost of two requests where one might fail.
