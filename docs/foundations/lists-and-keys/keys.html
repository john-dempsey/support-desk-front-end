Keys

Each row gets a key from the ticket's id, so React can tell the rows apart when the list changes.

Every row from .map() has a key:

  // React uses `key` to tell the rows apart when the list
  // changes. The ticket's id never changes, so it's a safe key.
  <tr key={ticket.id}>

Why React needs it

When a list changes (a ticket is added, deleted or sorted into a different order), React compares the new rows with the old ones and updates only what's different. It's much faster than rebuilding the whole table.

To compare, React has to know which new row is which old row. The key tells it: the row with key 3 before is the row with key 3 now, even if it has moved. Without keys, React can only match rows by their position: the first row with the first row, and so on.

key is only for React. It doesn't appear in the HTML, and a component can't read it as a prop.

Choosing a key

A key must be:

  • unique among the rows in that list, so no two rows are confused
  • stable: the same row must get the same key every time

The record's id is both, the same as a primary key in a database. So the rule is: use the record's id.

Why not the array index?

.map() can also give you each item's position (0, 1, 2, ...), and it's tempting to use that as the key. But positions aren't stable. Sort the list, or delete the first ticket, and key 0 now belongs to a different ticket. React then matches the wrong rows. In Stage 1 nothing visible goes wrong, because the rows hold nothing but text. Once rows hold anything that can change, such as a half-typed comment, it would end up next to the wrong ticket.
