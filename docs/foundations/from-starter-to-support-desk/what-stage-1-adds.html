What Stage 1 Adds

Two new pages, a list of tickets and one ticket, built on the starter, with the tickets hard-coded so the API isn't needed yet.

The starter's checklist ended with a plan for building in stages. The first step was:

Show your main entity with a list page and a detail page, using a hard-coded array before you fetch anything.

For Support Desk, the main entity is the ticket. Stage 1 takes that first step, and by the end of it the app has these pages:

URL Page Shows
/ HomePage a welcome and a link to the tickets
/tickets TicketListPage every ticket, in a table
/tickets/2 TicketDetailPage one ticket: its status, people, dates and description
anything else NotFoundPage unchanged from the starter

Each new page is added the way the checklist described: a page component in src/pages/, a <Route> in App.jsx, and a NavLink in NavBar.jsx.

One new thing at a time

The tickets in Stage 1 are a hard-coded array in the front-end. The API isn't involved at all, so you don't even need it running.

You've seen this approach before. In the back-end's Lesson 1, ticket.service.js kept its tickets in an in-memory array, and Lesson 2 swapped that array for real Prisma queries. Because the controllers only ever called the service, not one controller had to change.

Stage 1 does the same thing for the front-end. Building the pages first, with data you control, means:

  • if a page looks wrong, the problem is in how it displays tickets, not in a request, a token or the network
  • you can see every case straight away (an unassigned ticket, each status), without having to set it up in the database first
  • Stage 2 only has to change where the tickets come from. The parts that display them don't change at all.

Try it

Run npm run dev and open http://localhost:5173. Click Tickets, then click a ticket's subject. Now type http://localhost:5173/tickets/999 into the address bar. What does the page say? Is it the same page you get for http://localhost:5173/no-such-page?
