When There's No Such Ticket

/tickets/999 matches the route, but there's no ticket 999. The page says so itself, the way the API will answer 404 from Stage 2.

/tickets/999 matches /tickets/:ticketId, so React Router shows TicketDetailPage. But there's no ticket 999, so find() gives undefined. The page checks for that before anything else:

// Figure 1.28: no such ticket (src/pages/TicketDetailPage.jsx, excerpt)
// find() gives undefined when nothing matches, e.g. /tickets/999. The API
// will answer 404 in the same situation from Stage 2.
if (!ticket) {
  return (
    <>
      <h1>Ticket not found</h1>
      <p>There's no ticket with the ID "{ticketId}".</p>
      <p>
        <Link to="/tickets">Back to all tickets</Link>
      </p>
    </>
  );
}

It's an early return, like TicketList's empty state in topic 03. !ticket is true when ticket is undefined, so the page returns the message, and none of the code below it runs. That matters: the code below reads ticket.subject and ticket.customer.name, which would crash on undefined.

Why not NotFoundPage?

The starter's NotFoundPage is for a URL that matches no route, like /no-such-page. That's a different problem:

URL Route matched? Ticket found? Shown
/no-such-page no — NotFoundPage: "Page not found"
/tickets/999 yes no TicketDetailPage: "Ticket not found"
/tickets/2 yes yes TicketDetailPage: ticket 2

The page knows more than the router does, so it can say something more useful: which ID wasn't found, and a link back to the list rather than the home page. It shows ticketId exactly as it was typed, so /tickets/hello says there's no ticket with the ID "hello".

The same as a 404

In the back-end, GET /tickets/999 matched the /:id route, then the controller found no ticket and threw a 404. This page does the same thing on the front-end. From Stage 2 it will ask the API instead of using find(), and show this message when the API answers 404.
