From Code Values to Words

A lookup object turns the API's status values into the words a person should see, with a fallback for anything unexpected.

The API's status values are written for code: in_progress has an underscore and no capital letter. People should see In progress. StatusBadge translates with a lookup object:

// Figure 1.16: status labels (src/components/StatusBadge.jsx, excerpt)
// The API's status values are written for code ("in_progress"). These are
// the words a person should see instead.
const STATUS_LABELS = {
  open: 'Open',
  in_progress: 'In progress',
  resolved: 'Resolved',
  closed: 'Closed',
};

function StatusBadge({ status }) {
  // If the API ever sends a status this file doesn't know about, show it
  // as it is, in grey, rather than showing nothing.
  const label = STATUS_LABELS[status] || status;

Looking up a value

STATUS_LABELS[status] uses square brackets, because the key is in a variable. When status is 'in_progress', it reads STATUS_LABELS['in_progress'], which is 'In progress'.

STATUS_LABELS.status would be wrong: the dot looks for a key literally called status, and there isn't one.

A fallback with ||

If the API sends a status that isn't in the object (say a new on_hold status is added to the back-end one day), the lookup gives undefined. a || b gives b when a is undefined, so the badge shows the raw value, on_hold, instead of an empty badge. Not pretty, but honest, and the page keeps working.

Why an object, not ifs

The same thing could be written as four if statements. The object is shorter, and it's data, not logic: adding a status means adding one line, and you can see every label at a glance.

STATUS_LABELS is written outside the function, so it's created once when the file loads, not again every time the badge is drawn. Its capital letters mark it as a fixed value that never changes, the same as APP_NAME in NavBar.jsx.
