From the Page Down

The tickets pass down the tree one level at a time, and each component is given only the part it needs.

This is the path the tickets take from the array to the screen:

Only the page touches the data. Below it, everything gets its data as props, one level at a time.

Inside TicketList, each row is built from one ticket, called ticket (topic 03 shows where it comes from). These are three of the row's five cells (the two in between are left out):

// Figure 1.8: one row's cells (src/components/TicketList.jsx, excerpt)
<td>
  <Link to={`/tickets/${ticket.id}`}>{ticket.subject}</Link>
</td>
<td>
  <StatusBadge status={ticket.status} />
</td>
<td>{formatDate(ticket.createdAt)}</td>

Give each component only what it needs

StatusBadge is given ticket.status, not the whole ticket. It could have been written to take the ticket and read ticket.status itself, but then it could only ever be used where there's a whole ticket. Taking just a status means:

  • it can show any status, from anywhere: a ticket's row, a ticket's own page, or a page you haven't written yet
  • reading its one line, function StatusBadge({ status }), tells you everything it depends on
  • testing it only needs a status, not a whole made-up ticket

It's the same reason a back-end function takes an id rather than the whole req object.

A function, not a component

formatDate is in the diagram, but it isn't a component. It's an ordinary function that takes a date string and returns a string of text. So it's called inside { }, like any other JavaScript expression, instead of being written as a tag:

<td>{formatDate(ticket.createdAt)}</td>   // a function: call it
<StatusBadge status={ticket.status} />    // a component: use it as a tag

The rule of thumb: if it returns JSX, it's a component, and it's named in PascalCase. If it returns plain data, it's a function, named in camelCase, and it lives in src/utils/.
