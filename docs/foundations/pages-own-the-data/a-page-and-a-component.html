A Page and a Component

TicketListPage gets the tickets; TicketList shows them. One decides what to show, the other decides how it looks.

The Tickets page is split across two files. The page is short:

// Figure 1.6: the Tickets page (src/pages/TicketListPage.jsx)
import TicketList from '../components/TicketList.jsx';
import sampleTickets from '../data/sampleTickets.js';

function TicketListPage() {
  return (
    <>
      <h1>Tickets</h1>
      <TicketList tickets={sampleTickets} />
    </>
  );
}

export default TicketListPage;

It does two things: it gets the tickets (for now, by importing the array), and it hands them to TicketList as a prop called tickets.

TicketList does the displaying: the table, its headings and one row per ticket. It starts like this:

// Figure 1.7: the list's one prop (src/components/TicketList.jsx, excerpt)
function TicketList({ tickets }) {

That one line is everything TicketList knows about where its data comes from: somebody passes it tickets. It never imports sampleTickets, and it will never call the API.

Two kinds of component

Both files are components (functions that return JSX), but they have different jobs, and they live in different folders:

Pages (src/pages/) Components (src/components/)
Job get the data, decide what to show show what they're given, decide how it looks
Gets its data from an import now; the API from Stage 2 its props only
Used once, by a <Route> in App.jsx anywhere, by any page
Back-end / Laravel equivalent a controller a Blade view or partial

The starter compared pages with controllers, and the comparison carries on here. In Laravel, a controller loaded the tickets and passed them to a view:

return view('tickets.index', ['tickets' => $tickets]);

The Blade view never ran a query. It looped over the $tickets it was given. <TicketList tickets={sampleTickets} /> is the same handover: TicketListPage is the controller, and TicketList is the view.
