When a Date Is Bad

new Date() doesn't fail on a bad string. It gives an Invalid Date, and formatting that would crash the page, so formatDate checks first.

What if a date is missing, or isn't a date at all? Here's the whole function:

// Figure 1.23: checking the date (src/utils/formatDate.js, excerpt)
export function formatDate(isoString) {
  const date = new Date(isoString);

  // new Date() doesn't throw for a bad string; it gives an "Invalid Date"
  // whose time is NaN. Without this check, format() would throw and the
  // whole page would crash because of one bad date.
  if (Number.isNaN(date.getTime())) {
    return 'Unknown date';
  }

  return dateFormatter.format(date);
}

A quiet failure, then a loud one

new Date('not a date') doesn't throw an error. It gives back a Date object anyway, an Invalid Date. You only find out when you use it:

  • date.getTime() (the date as a number of milliseconds) is NaN, "not a number"
  • dateFormatter.format(date) throws: RangeError: Invalid time value

You saw in topic 03 what one error while drawing does: the whole app goes blank. One bad date in one row would take the whole Tickets page with it.

The check

Number.isNaN(date.getTime()) is the reliable way to ask "is this an Invalid Date?". (NaN is the one value that isn't equal to itself, so date.getTime() === NaN is always false, and can't be used.) If the date is invalid, the function returns 'Unknown date' and never calls format().

The API should never send a bad date. But formatDate can't know where its string came from, so it handles the bad case itself and says so honestly, rather than trusting every caller.
