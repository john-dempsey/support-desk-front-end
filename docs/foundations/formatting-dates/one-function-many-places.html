One Function, Many Places

formatDate is a plain function in src/utils/, used by both ticket pages, the same way the back-end keeps small shared helpers in its utils folder.

Three places in Stage 1 show a date: the Created column in TicketList, and the Created and Last updated rows on TicketDetailPage. All three call the same function, like the {formatDate(ticket.createdAt)} cell in Figure 1.8.

So every date in the app looks the same, and changing how dates look means changing one file. Try it in the previous slide's Try it if you haven't: one change to 'en-US' changed every date on every page.

Why src/utils/

formatDate doesn't return JSX, so it isn't a component (topic 02). It doesn't belong to a page, and it doesn't talk to the API. It's a small, general-purpose helper, so it goes in src/utils/, the same idea as the back-end's utils/ folder, which holds helpers like sendResource() in response.js.

A named export

Components are default exports (export default TicketList;), imported without braces. formatDate.js uses a named export instead, like the back-end's utils/response.js. Shortened, the two ends look like this:

// in formatDate.js
export function formatDate(isoString) { /* ... */ }

// in TicketList.jsx
import { formatDate } from '../utils/formatDate.js';

With a named export, the braces must use the exported name exactly. A utils file can then grow to hold several related helpers, each imported by name, just like sendResource and sendCollection in the back-end.

Easy to test

Because formatDate is just a function (string in, string out, no React, no browser page), its test only has to call it and check what comes back. Topic 07 shows that test.
