Dates From the API

JSON has no date type, so the API sends every date as an ISO 8601 string. The front-end decides how a person should see it.

Every ticket has two dates, createdAt and updatedAt, and the API sends both as strings, like this:

"createdAt": "2026-10-08T09:15:00.000Z"

JSON has numbers, strings, booleans, arrays and objects, but no date type. So when Express turned Prisma's Date objects into JSON, it wrote each one as a string in the ISO 8601 format.

Reading an ISO date

Part Means
2026-10-08 the date: year, month, day, biggest first
T separates the date from the time
09:15:00.000 the time: hours, minutes, seconds, milliseconds
Z the time is in UTC (no time zone offset)

It's a good format for computers: there's only one way to read it (10-08 is never "10 August"), and sorting the strings alphabetically sorts the dates too.

It's not a good format for people. Nobody wants to read 2026-10-08T09:15:00.000Z in a table.

Why the front-end formats it

The API could have sent "8 Oct 2026" instead. But the API doesn't know who's looking:

  • the time zone. 09:15 UTC is 10:15 in Ireland in October, and 05:15 in New York. Only the browser knows where the user is.
  • the language. Irish English writes 8 Oct 2026; American English writes Oct 8, 2026.
  • the purpose. One page might want the full date and time, another just the day.

So the API sends one exact, neutral value, and each client formats it for its own user. In Laravel, Blade did this on the server with Carbon ($ticket->created_at->format('j M Y')), because the server was building the page. Here, the page is built in the browser, so that's where the formatting happens.
