Testing a Component With Props

StatusBadge only uses its props, so its test renders it with different props and checks what a user would read.

StatusBadge has no links, no URL and no API, just a status prop. So its test can use a plain render(), the way the starter's tests did:

// Figure 1.32: badge tests (src/components/StatusBadge.test.jsx, excerpt)
describe('StatusBadge', () => {
  it('shows a readable label for the status', () => {
    render(<StatusBadge status="in_progress" />);

    expect(screen.getByText('In progress')).toBeInTheDocument();
  });

  it('shows an unknown status as it is', () => {
    render(<StatusBadge status="on_hold" />);

    expect(screen.getByText('on_hold')).toBeInTheDocument();
  });
});

Testing a component with props is like calling a function with arguments: give it an input, check the output. Each test passes a different status, and checks the words that appear.

Which cases to test

The two tests cover the two paths through StatusBadge:

  • a status it knows: does the lookup turn in_progress into In progress?
  • a status it doesn't know: does the || fallback show the raw value instead of nothing?

There's no need for a test per status. open, resolved and closed go through exactly the same line as in_progress, so one test covers that path.

What it doesn't test: the colour

There's no test that an in_progress badge is yellow. The colour comes from a generated class name like _in_progress_85lrl_23, and the starter's rule was not to test class names: a user can't see them, and renaming one would break the test without breaking anything the user notices. What the user must get, the status in words, is exactly what the tests check. That's also the part that makes the badge accessible.

Try it

Write a third test in StatusBadge.test.jsx that checks a resolved status shows Resolved. Run npm test and check it passes. Then break it on purpose: change Resolved in STATUS_LABELS to Done. Which tests fail? Put it back.
