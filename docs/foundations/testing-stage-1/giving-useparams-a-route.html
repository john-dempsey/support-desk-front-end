Giving useParams() a Route

useParams() only knows a parameter when a <Route> with that pattern matched, so the page test passes both the URL and the pattern.

TicketDetailPage reads ticketId with useParams(). In the app, App.jsx's <Route path="/tickets/:ticketId"> is what tells React Router there is a parameter called ticketId, and which part of the URL it is. A test that renders the page on its own has no <Route>, so useParams() returns an empty object, ticketId is undefined, and the page always says "Ticket not found".

So the page's tests pass two options:

// Figure 1.34: a page that reads the URL
// (src/pages/TicketDetailPage.test.jsx, excerpt)
const DETAIL_PATH = '/tickets/:ticketId';

it('shows the ticket whose ID is in the URL', () => {
  renderWithProviders(<TicketDetailPage />, {
    route: '/tickets/2',
    path: DETAIL_PATH,
  });

  expect(
    screen.getByRole('heading', { level: 1, name: 'Invoice discrepancy' }),
  ).toBeInTheDocument();
  expect(screen.getByText('Charged twice for March')).toBeInTheDocument();

(In the file, this test sits inside describe('TicketDetailPage', ...), and the renderWithProviders call is one line. Both are changed here to fit.)

  • route is the URL to start at, like typing it in the address bar.
  • path is the pattern, the same as in App.jsx. With it, the helper wraps the page in a <Routes> with one <Route> (Figure 1.33), so React Router matches /tickets/2 against /tickets/:ticketId and useParams() gives { ticketId: '2' }.

DETAIL_PATH is a constant so that all four tests use the same pattern.

The other tests

The file's other three tests check the cases from topic 06:

  • /tickets/999 shows Ticket not found
  • /tickets/abc shows Ticket not found (Number('abc') is NaN)
  • the Back to all tickets link points to /tickets

This page still uses sampleTickets, so these tests rely on ticket 2 being "Invoice discrepancy". When Stage 2 replaces the sample data with the API, these tests will have to change too.
