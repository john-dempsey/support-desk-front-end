Calling It on a 401

apiRequest() calls the handler when a request that carried a token gets a 401. A wrong password also gets a 401, but carried no token, so it doesn't log anyone out.

// Figure 4.31: noticing the 401 (src/api/client.js, excerpt)
// response.ok is true for any 2xx status. Anything else is an error, and
// the back-end puts its explanation in { error: { message, details } }.
if (!response.ok) {
  // A 401 to a request that carried a token means the session is over.
  // (A 401 with no token, such as a wrong password at login, doesn't.)
  if (response.status === 401 && token && sessionExpiredHandler) {
    sessionExpiredHandler();
  }

  const message = responseBody?.error?.message
    || `Request failed with status ${response.status}`;
  throw createApiError(
    response.status, message, responseBody?.error?.details
  );
}

(Indented one step further in the file. The message and throw lines are one line each there, as in Figure 2.6.)

Only the inner if is new. Three things must all be true:

Condition Why
response.status === 401 the API says the token is no good
token this request carried a token. That's why apiRequest() reads the token once, at the start (Figure 4.7): it needs to know now what it sent then
sessionExpiredHandler someone has put a function there. In tests that use client.js on its own, nobody has

Not every 401 is a session ending

A wrong password at login also gets a 401: "Invalid email or password". But nobody is logged in yet, so no token was sent, token is null, and the handler isn't called. The login page just shows the message (topic 06). That's why LoginPage and RegisterPage didn't count on the last slide: their 401s are about the details typed in.

Then it throws, as before

After calling the handler, apiRequest() still throws the error. The page that sent the request still gets it in its catch, exactly as in Stage 3. Nothing in any page had to change. The page is about to be replaced by the login page anyway (the next slide shows how).
