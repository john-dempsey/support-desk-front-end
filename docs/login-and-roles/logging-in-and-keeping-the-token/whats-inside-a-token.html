What's Inside a Token

Anyone can read a token's payload: it holds the user's id, their role, and when it expires. The app could decode it, but doesn't need to, and shouldn't trust what it finds.

A token looks like random text, but it isn't. Lesson 4's "What Is a JWT?" showed it has three parts, separated by dots:

eyJhbGciOiJIUzI1NiIs….eyJzdWIiOjMsInJvbGUiOiJjdXN0b21lciIs….Xk2p…
   header                     payload                          signature

The middle part, the payload, is JSON written in base64, a way of writing any data as plain letters and digits. The browser can turn it back with atob().

Reading Casey's token

With Casey logged in, open the DevTools Console and type these four lines, pressing Enter after each one:

const token = localStorage.getItem('supportDeskToken');
const encodedPayload = token.split('.')[1];
const payload = JSON.parse(atob(encodedPayload));
payload;

Line by line:

  1. Read the saved token, the same way getSavedToken() does.
  2. Split it at the dots, and keep the middle part. split('.') gives an array of the three parts, and [1] is the second: the payload, still in base64.
  3. atob() turns the base64 back into JSON text, and JSON.parse() turns that text into an object, saved as payload.
  4. Show payload.

You'll see something like:

{ sub: 3, role: 'customer', iat: 1792154967, exp: 1792241367 }
Field Meaning Where from
sub the user's id ("subject") signToken({ sub: user.id, role: user.role }) in auth.controller.js
role the user's role the same line
iat "issued at": when the token was made added by jsonwebtoken
exp when it expires added by jsonwebtoken, from JWT_EXPIRES_IN

iat and exp are in seconds since 1 January 1970. exp - iat is 86400: 24 × 60 × 60, one day. That's why a token from yesterday doesn't work today.

Signed, not secret

Nothing here was hidden: anyone holding the token can read it. What they can't do is change it. Changing the role to "admin" would break the signature, and authenticate.js would answer 401. Only the back-end has the secret that makes a valid signature.

Why the app doesn't decode it

The app could read role out of the token. It doesn't, for two reasons:

  • It can't check it. The browser doesn't have the secret, so it can't tell a real token from an edited one. Whatever it decoded would be unchecked.
  • It doesn't need to. The login answer and GET /auth/me already give the user, role included, checked by the API.

So to the front-end, the token is a sealed envelope: it saves it, sends it, and never opens it.

Try it

  1. With Casey's payload still in the Console from the four lines above, type new Date(payload.exp * 1000). (* 1000 because a JavaScript Date counts in milliseconds, not seconds.) When does Casey's token stop working?
  2. Log out, log in as Alex, and run the four lines again. Which fields are different from Casey's?

If Chrome won't let you paste into the Console, type allow pasting first. (atob() reads ordinary base64. A JWT uses a URL-safe version that can contain - and _, and atob() would refuse those. The Support Desk's short payloads don't contain them.)
