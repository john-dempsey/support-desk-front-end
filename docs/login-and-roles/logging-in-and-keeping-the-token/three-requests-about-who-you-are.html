Three Requests About Who You Are

auth.api.js has one function per auth route: log in, register, and ask who a token belongs to. They follow the same three steps as every other API function.

Stage 4's new API file follows the pattern from Stage 3, topic 02: call apiRequest(), wait, return what's in data.

// Figure 4.2: logging in, and asking who you are
// (src/api/auth.api.js, excerpt)
// POST /auth/login: returns { user, token }. A wrong email or password is
// a 401 "Invalid email or password" (the API doesn't say which was wrong).
export async function login(email, password) {
  const responseBody = await apiRequest('/auth/login', {
    method: 'POST',
    body: { email, password },
  });
  return responseBody.data;
}

export async function getCurrentUser() {
  const responseBody = await apiRequest('/auth/me');
  return responseBody.data;
}

(getCurrentUser()'s comment is left out here.)

register(name, email, password) is the same as login(), with a different path and a name in the body.

What each one sends and gets back

Function Sends Answer
login(email, password) POST /auth/login 200 { data: { user, token } }
register(name, email, password) POST /auth/register 201 { data: { user, token } }, always a customer
getCurrentUser() GET /auth/me, with the token 200 { data: { id, name, email, role, createdAt } }

A successful login looks like this:

{
  "data": {
    "user": {
      "id": 3,
      "name": "Casey Customer",
      "email": "casey@example.com",
      "role": "customer",
      "createdAt": "2026-10-14T20:04:29.739Z"
    },
    "token": "eyJhbGciOiJIUzI1NiIs…"
  }
}

(The token is cut short. Your ids and dates will be different.)

Two things in one answer: who you are (user), and proof of it for later requests (token). The front-end keeps both, in different places. The next slide shows where the token goes.

No token needed to get a token

login() and register() work without a token: the back-end's auth.routes.js deliberately has no authenticate on them, since they're how a client gets one. GET /auth/me is the opposite. It only makes sense with a token, and asks the API "whose is this?".

auth.api.js only sends requests. It doesn't save the token or remember the user. That's AuthProvider's job, later in this lesson, and it's the only file that calls these three functions.

Try it

In your REST client, send POST /auth/login with Casey's email and the wrong password. Then send it with an email that doesn't exist. Compare the two answers. Why does the API send the same message for both? (Lesson 4, "Login: One Message for Two Failures".)
