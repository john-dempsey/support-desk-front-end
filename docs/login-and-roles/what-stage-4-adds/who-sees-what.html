Who Sees What

Each page and control now depends on who is logged in. The front-end makes the same decisions as the back-end's authenticate and authorize, for the user's sake.

In Stage 3, everyone saw everything. In Stage 4, what you see depends on who you are:

Three kinds of decision

  1. Logged in or not. The blue → /login column is the front-end's version of the back-end's authenticate.js: no token, no ticket pages.
  2. Which role. The grey "Not available" cells are its version of authorize(...). Figure 4.1 shows how one is written.
  3. Which tickets. "Their own" and "theirs + unassigned" aren't decided by the front-end at all. The API only sends each user the tickets they may see (Lesson 4, "Role-Scoped Queries"). The list page shows whatever comes back, exactly as in Stage 3.

A page for customers only

Here's the route for the new ticket page:

// Figure 4.1: a page only customers can open (src/App.jsx, excerpt)
<Route
  path="/tickets/new"
  element={
    <ProtectedRoute allowedRoles={['customer']}>
      <NewTicketPage />
    </ProtectedRoute>
  }
/>

and here's the back-end route it matches, in ticket.routes.js:

router.post(
  '/',
  authorize('customer'),
  validate({ body: createTicketSchema }),
  ticketController.createTicket,
);

Same rule, same words: customer. Topic 07 shows how ProtectedRoute works.

The back-end still decides

The front-end's checks are there so nobody is shown a page or a button that can only fail. They don't protect anything: the API checks every request itself, as it always has. The note under the grid says so.
