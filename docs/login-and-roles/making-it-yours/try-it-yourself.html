Try It Yourself

Challenges that use everything in this lesson. Run the tests after each one, and commit when they pass.

Each of these builds on something from this lesson. After each one, run npm test and npm run lint, and commit when both pass.

Warm-up

  1. Welcome back. On the home page, show "Welcome back, Casey" to a logged-in user. Which value from useAuth() do you need? Add a test with renderWithProviders(<HomePage />, { user: customerUser }), and one for a visitor.
  2. Show the password. Add a Show password checkbox under the password field on the login page, which switches the input's type between password and text. Where does its state belong? Make sure it has a <label>. Test it.

Build something

  1. Assign to me. On an unassigned ticket's page, show an agent an Assign to me button, which sends PATCH with { "assignedAgentId": <their id> } and updates the page from what updateTicket() returns. Where does the agent's id come from? Who should see the button, and who shouldn't? Test both.
  2. Edit your own comment. The API lets a comment's author (or an admin) change it with PATCH /tickets/:ticketId/comments/:id. Add updateComment(), and an Edit button on each comment the user may edit. Is the rule the same as canDelete? Could one function serve both? Test it as Casey and as Ada.
  3. Your session has expired. When the session-expired handler logs someone out, the login page just appears, with no explanation. Make it say "Your session has expired. Please log in again." Where should the "it expired" fact be kept, so LoginPage can read it? When should it be cleared? Make sure a wrong password doesn't show it.

Investigate

  1. Two tabs. Log in as Casey, and open the ticket list in two tabs.

    • In the second tab, log out. Back in the first, which still shows Casey's name, click a ticket. What do you see, and what did the ticket request get back? Why wasn't the session-expired handler called?
    • Log in as Casey in both tabs again. In the second, log out and log in as Alex. In the first, still saying "Casey", click a ticket. Whose token was sent?

    Both tabs share one localStorage, but each has its own user state. The browser fires a storage event in the other tabs when localStorage changes. How could AuthProvider use it?

  2. The rate limit. On the login page, count your attempts until "Too many attempts" appears. Do successful logins count? Check RateLimit-Remaining after each. Then find, in the back-end, where the limit of 10 is set.

  3. What a new account can do. Register a new account. Decode its token in the Console (topic 02). What's its role? Find the line in the back-end that decided it.

Commit

git add .
git commit -m "Stage 4: welcome back, assign to me, ..."

When your own case study's users can log in and register, stay logged in across a reload, see only the pages and buttons their role can use, and are logged out when their token expires, with tests for each, your front-end has caught up with your back-end's authentication.
