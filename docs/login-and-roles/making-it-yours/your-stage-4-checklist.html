Your Stage 4 Checklist

The same steps for your own case study: log in and register, keep the token, check it on load, protect pages, show controls by role, and log out on a 401.

Only if your API has authentication. If it doesn't, your app is complete at Stage 3 (topic 01).

Here's how to add Stage 4 to your own front-end, in the order this lesson did it. The examples use a booking system; swap in your own roles and entities. Run npm test and try the app in the browser after every step, and commit when both work.

0. Check your API

In your REST client, find out:

  • what your login and register routes are called, what they take, and what they answer. The Support Desk sends { data: { user, token } }. Yours may differ, and auth.api.js will need to match it.
  • your role names, exactly as the API spells them.
  • whether you have a "who am I" route like GET /auth/me. If not, add one to your back-end: Lesson 7 shows how. Without it, the app can't check a saved token when it starts.

1. Logging in, and keeping the token

auth.api.js (Figure 4.2), and tokenStorage.js with your own key name (Figure 4.3). Change getToken() in client.js (Figure 4.6), and delete VITE_DEV_TOKEN from .env and .env.example.

2. The context

authContext.js as it is (Figure 4.8). AuthProvider.jsx with user, login(), register(), logout() and hasRole() (Figures 4.9, 4.11 and 4.12). Wrap <App /> in main.jsx (Figure 4.10).

3. Checking the session

isCheckingSession, the /auth/me effect, and the wait in App.jsx (Figures 4.14 to 4.16). Reload while logged in: you should stay logged in, on the same page.

4. Login and register pages

LoginPage and RegisterPage at /login and /register, each with if (user) to leave (Figures 4.17 to 4.21). Copy your register schema's rules into the inputs. Reuse FieldError and getFieldError() from Stage 3. Adapt describeAuthError() to the messages your API sends.

5. Protected pages

Copy ProtectedRoute.jsx as it is (Figure 4.23). Wrap each page in App.jsx, with allowedRoles matching each back-end route's authorize(...) (Figure 4.22).

6. Controls by role

NavBar: links by role, the user's name, Log out (Figures 4.24 and 4.25). Then one hasRole() check around each button that only some roles can use (Figures 4.26 and 4.27). If a rule depends on the record (like "only your own comments"), use a function prop (Figures 4.28 and 4.29).

7. When the session ends

setSessionExpiredHandler() in client.js, the 401 check in apiRequest(), and the effect in AuthProvider (Figures 4.30 to 4.32).

8. Tests

  • testUsers.js with one user per role, and the user option in renderWithProviders (Figure 4.33). Pick a default that sees every control, so your Stage 3 tests keep passing.
  • AuthProvider.test.jsx with a ShowAuth component (Figures 4.37 and 4.38), and localStorage.clear() in setup.js.
  • ProtectedRoute, the login and register pages, and a "yes" and "no" test for each control by role.
  • The two 401 tests in client.test.js (Figure 4.39).
