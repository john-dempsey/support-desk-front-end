Hiding Is Not Security

Every check in the front-end can be skipped: the code runs on the user's computer. The API's checks are the ones that keep the data safe. The front-end's make the app easier to use.

Stage 3 said it, and Stage 4 has now built it: the front-end hides what a role can't use. It's worth being clear about what that does, and what it doesn't.

The front-end runs on the user's computer

Everything in src/ is downloaded to the browser. The user can read it in DevTools' Sources tab, change it, or skip it entirely and send requests with a REST client. No check in the front-end can stop that.

So:

Front-end Back-end
Where it runs the user's browser your server
Who controls it the user you
Its checks are for the user's convenience: no buttons that can only fail security: no request gets through that shouldn't
If its check is missing the user sees a button, clicks, gets a 403 anyone can do anything

Try it

The front-end now hides these buttons from Casey. Go around it: in your REST client, log in as Casey, and use Casey's token for these:

  1. GET /tickets/1/comments. Find the id of Alex's comment.
  2. DELETE /tickets/1/comments/<that id>. What comes back?
  3. PATCH /tickets/1 with the body { "status": "closed" }. What comes back, and which line of the back-end's ticket.routes.js sent it?

The front-end never showed Casey a button for either. The API refused anyway, because it checks every request itself, whoever sends it. That's the only reason it's safe for the front-end's checks to be "just" for convenience.
