Testing the 401

Two client.js tests pin down when the session-expired handler is called: a 401 with a token, yes; a 401 without one, no. A vi.fn() stands in for the handler.

client.js is tested on its own, with a fake fetch(), as in Stage 0. Two new tests check the rule from topic 09, one for each side of it:

// Figure 4.39: when the handler is called (src/api/client.test.js,
// excerpt)
it('calls the session-expired handler for a 401 when a token was sent',
  async () => {
    const handleSessionExpired = vi.fn();
    setSessionExpiredHandler(handleSessionExpired);
    saveToken('expired-token');
    fakeFetchResponding(401, {
      error: { message: 'Invalid or expired token' },
    });

    await expect(apiRequest('/tickets'))
      .rejects.toMatchObject({ status: 401 });

    expect(handleSessionExpired).toHaveBeenCalled();
    setSessionExpiredHandler(null);
  });

(Split to fit.)

A vi.fn() as the handler

The test doesn't need AuthProvider. It puts a vi.fn() where AuthProvider would put its function, and checks it was called. That tests client.js's part of the job, and only that part.

The last line takes the handler away again. The vi.fn() would otherwise stay in client.js for the tests after this one.

The other side

The next test is the same, but with no saveToken(), a request to /auth/login, and the message "Invalid email or password". It ends:

expect(handleSessionExpired).not.toHaveBeenCalled();

Together, the two tests pin the rule down: remove && token from client.js, and the second fails; remove the whole if, and the first fails.

The whole chain

One more test, in AuthProvider.test.jsx, joins the two halves: the real AuthProvider, logged in, and the real apiRequest() with a fake fetch() answering 401. It checks that ShowAuth then says "Logged out" and the token is gone. That's the diagram from topic 09, tested from step 2 to step 5.

Try it

In client.js, remove && token from the 401 check. Run the tests. Which one fails?

Now think it through. Today, would anyone using the app notice? (Who is logged in when someone types a wrong password, and what do clearSavedToken() and setUser(null) change then?) Then imagine the handler also showed a message: "Your session has expired. Please log in again." What would a user with a mistyped password see? That's why the test is worth keeping. Put && token back when you're done.
