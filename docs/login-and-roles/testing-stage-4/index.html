Testing Stage 4

A fake logged-in user for page tests, the real AuthProvider tested on its own, the 401 handler, and a whole visit from login to logout.

  • What Stage 4 Tests

    Most page tests fake who is logged in. AuthProvider is tested on its own, with only its API calls faked. And one test follows a whole visit through the real app.

  • A Fake Logged-In User

    renderWithProviders now fills the auth context with a fake value. A test says who is logged in with `user`, and Ada is the default, so Stage 3's tests didn't change.

  • Testing by Role

    A role test renders the same page as different users, and checks what's there and what isn't. queryBy... finds nothing without failing, so it can prove a button is missing.

  • Checking What the Page Asked For

    In a page test, login() is a vi.fn(). The test checks it was called with what was typed, and makes it fail to see how the page shows the error.

  • Where Does It Send You?

    ProtectedRoute's tests put it in a tiny route table, with plain headings standing in for the real pages, and check which heading appears for each user.

  • Testing the Real AuthProvider

    AuthProvider has no screen of its own, so its tests put a tiny component inside it that shows what useAuth() gives. Only auth.api.js is faked; localStorage is real.

  • Testing the 401

    Two client.js tests pin down when the session-expired handler is called: a 401 with a token, yes; a 401 without one, no. A vi.fn() stands in for the handler.

  • A Whole Visit

    One App test uses the real AuthProvider with only the API modules faked, and follows a visit from start to finish: log in, move around, log out, and log in as someone else.

  • Running Everything

    Stage 4 ends with 122 passing tests in 24 files, no lint warnings and a working build, with no token in .env.
