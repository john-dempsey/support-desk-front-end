Where Does It Send You?

ProtectedRoute's tests put it in a tiny route table, with plain headings standing in for the real pages, and check which heading appears for each user.

ProtectedRoute decides between three outcomes (topic 07). Its tests don't need any real pages to check that. Plain headings stand in for them:

// Figure 4.36: a route table made for the test
// (src/components/ProtectedRoute.test.jsx, excerpt)
function renderTagsRouteAs(user) {
  renderWithProviders(
    <Routes>
      <Route
        path="/tags"
        element={
          <ProtectedRoute allowedRoles={['agent', 'admin']}>
            <h1>Tags page</h1>
          </ProtectedRoute>
        }
      />
      <Route path="/login" element={<h1>Login page</h1>} />
    </Routes>,
    { route: '/tags', user },
  );
}

it('sends a visitor who is not logged in to the login page', () => {
  renderTagsRouteAs(null);

  expect(screen.getByRole('heading', { name: 'Login page' }))
    .toBeInTheDocument();
});

(Split to fit, and two of the three tests are left out.)

<h1>Tags page</h1> is the children. If it appears, ProtectedRoute returned its children. If "Login page" appears, the <Navigate> took the router to /login. Stage 3 used the same trick to check where a page went after saving (Stage 3, topic 10, "Where Did It Go?").

The three tests call renderTagsRouteAs() with null, customerUser and agentUser: one per outcome.

No waiting needed

These tests don't await anything. ProtectedRoute decides from user straight away, and Testing Library's render() finishes React's work, including the <Navigate>, before it returns. Nothing is fetched, so there's nothing to wait for.

The real route table, too

App.test.jsx checks the same thing through the real App: a visitor on /tickets sees the login page, and getTickets was never called. That second check proves the page didn't even start loading, which is the point of ProtectedRoute.

Try it

In ProtectedRoute.jsx, swap the two if blocks, so the role check comes first. Before you run the tests, predict which one will fail. Then run them. Were you right? What does the visitor see instead of the login page? Put the blocks back when you're done.
