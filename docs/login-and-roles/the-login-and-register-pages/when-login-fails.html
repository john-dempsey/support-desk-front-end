When Login Fails

A wrong password shows the API's message at the top of the form. An email the browser accepts but the API doesn't shows its message next to the email field, with Stage 3's FieldError.

// Figure 4.19: the email field (src/pages/LoginPage.jsx, excerpt)
<form className="form" onSubmit={handleSubmit}>
  {loginError && <ErrorMessage message={loginError.message} />}

  <div className="form-field">
    <label htmlFor="login-email">Email</label>
    <input
      id="login-email"
      type="email"
      autoComplete="email"
      required
      value={email}
      onChange={(event) => setEmail(event.target.value)}
      aria-invalid={Boolean(emailError)}
      aria-describedby={emailError ? 'login-email-error' : undefined}
    />
    <FieldError id="login-email-error" message={emailError} />
  </div>

(Less indented here than in the file, and a comment is left out.) emailError is getFieldError(loginError, 'email'), as in Stage 3.

Three kinds of failure

What happens Answer Shown
Wrong email or password 401 "Invalid email or password" at the top, by ErrorMessage
An email the API rejects 400 "Validation failed", with details at the top, and "Invalid email" under the field
Too many attempts 429 at the top, reworded (next slide)

The 400 reuses Stage 3's pieces unchanged: getFieldError() finds the message for email, and FieldError shows it, linked to the input with aria-describedby.

Two checks of one email

type="email" and required make the browser check the form before it's sent. But the browser and the API don't agree on what an email address is. To the browser, casey@example is fine: a name, an @, and a domain. The API's Zod .email() wants a dot in the domain, so it answers 400.

So the browser's checks are for the user's convenience, and the API's are the ones that count. The page has to show the API's answer, whatever the browser let through.

autoComplete

autoComplete="email", and "current-password" on the password field, tell the browser and password managers what each field is for, so they can fill them in. The register page uses "new-password" instead, so a password manager offers to make up a strong one.

Try it

  1. Log in with the email casey@example (no .com) and any password. Where does each message appear?
  2. Log in as Casey with the wrong password. Now which message shows, and where?
  3. Try casey (no @ at all). Who stops it this time, the browser or the API? How can you tell from the Network tab?

Each attempt that reaches the API counts towards its limit of 10 every 15 minutes. If you see "Too many attempts", wait a few minutes.
