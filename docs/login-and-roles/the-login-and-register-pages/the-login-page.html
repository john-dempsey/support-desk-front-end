The Login Page

LoginPage holds what's typed, calls login() from useAuth(), and on success does nothing at all: the new user makes the page leave by itself.

The login form is only used on one page, so it's written inside the page. In Stage 3, TicketForm was a separate component because two pages used it. Here there's nothing to share.

// Figure 4.17: logging in (src/pages/LoginPage.jsx, excerpt)
function LoginPage() {
  const { user, login } = useAuth();
  const [email, setEmail] = useState('');
  const [password, setPassword] = useState('');
  const [loginError, setLoginError] = useState(null);
  const [isSubmitting, setIsSubmitting] = useState(false);

  // ... if (user): the next slide

  async function handleSubmit(event) {
    event.preventDefault();
    setLoginError(null);
    setIsSubmitting(true);
    try {
      await login(email, password);
    } catch (error) {
      setLoginError(describeAuthError(error));
      setIsSubmitting(false);
    }
  }

(The // ... line stands for code that's left out here.)

Most of this is Stage 3 again:

  • Controlled inputs: email and password hold what's typed, as in TicketForm.
  • isSubmitting disables the button while the request is on its way, so a double-click doesn't log in twice.
  • The whole error is kept, not just its message, so the form can find the details for the email field.

login() comes from useAuth()

The page doesn't call auth.api.js itself. It calls login() from the context, which asks the API, saves the token and sets the user (topic 04). If anything goes wrong, login() throws, and the catch here shows it.

On success: nothing

Look at the try: after await login(...), there's nothing. No navigate(), no message, and isSubmitting is never set back to false. Yet after a successful login, you end up on the ticket list.

That's because login() changed user, and LoginPage reads user from useAuth(). So the page re-renders, with a user this time, and the next slide shows what it does then.
