ProtectedRoute, Line by Line

Three questions, three outcomes: nobody logged in goes to /login, the wrong role sees "Not available", and everyone else gets the page.

// Figure 4.23: deciding what to show
// (src/components/ProtectedRoute.jsx, excerpt)
function ProtectedRoute({ allowedRoles, children }) {
  const { user, hasRole } = useAuth();

  if (!user) {
    // `replace` swaps this URL for /login in the browser's history, so the
    // Back button doesn't bring the user straight back here.
    return <Navigate to="/login" replace />;
  }

  if (allowedRoles && !hasRole(...allowedRoles)) {
    return (
      <>
        <h1>Not available</h1>
        <p>Your account can't use this page.</p>
        <p>
          <Link to="/tickets">Go to the tickets</Link>
        </p>
      </>
    );
  }

  return children;
}

No user: go to the login page

<Navigate>, as on the login page (topic 06), with replace. Without replace, pressing Back on the login page would return to the protected URL, which would send the user straight back to the login page: Back would seem to do nothing.

Wrong role: say so

allowedRoles && comes first: with no allowedRoles (as for /tickets), there's nothing to check, and any logged-in user may see the page. Otherwise, hasRole(...allowedRoles) spreads the array back into separate arguments, hasRole('agent', 'admin'), the call from topic 04.

The order of the two ifs matters. Someone who isn't logged in has no role at all, so they'd fail the role check too, and see "Not available" instead of being sent to log in.

Otherwise: the page

return children returns the page exactly as App.jsx wrote it. ProtectedRoute adds nothing around it.
