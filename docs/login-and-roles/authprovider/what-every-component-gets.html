What Every Component Gets

useAuth() gives six things: the user, whether the session is being checked, login(), register(), logout() and hasRole(). The token isn't one of them.

Here's the whole of authValue, and who uses each part:

Name What it is Used by
user the logged-in user, or null NavBar, ProtectedRoute, HomePage, LoginPage, RegisterPage, TicketDetailPage
isCheckingSession true while a saved token is being checked App (topic 05)
login(email, password) log in LoginPage
register(name, email, password) create a customer account, and log in RegisterPage
logout() forget the token and the user NavBar
hasRole(...roles) is the user one of these roles? NavBar, ProtectedRoute, TicketListPage, TicketDetailPage

This is the only way the rest of the app learns about the logged-in user. A component never imports tokenStorage.js or auth.api.js, and never calls setUser(): it uses what useAuth() gives it.

No token

The token isn't in authValue, on purpose:

  • No component needs it. client.js already adds it to every request, by reading it from localStorage (topic 02).
  • What isn't handed out can't be misused. A component can't log it, show it, or send it somewhere by mistake if it never has it.

The same shape in tests

Tests can't log in to a real API, so renderWithProviders fills the same context with a fake value of the same shape:

// Figure 4.13: a fake value for tests
// (src/test/renderWithProviders.jsx, excerpt)
function createFakeAuth(user) {
  return {
    user,
    isCheckingSession: false,
    login: vi.fn(),
    register: vi.fn(),
    logout: vi.fn(),
    hasRole: (...roles) => user !== null && roles.includes(user.role),
  };
}

A component can't tell the difference. It calls useAuth() and gets an object with the same six names. Topic 10 shows how the tests use it.
