Who Needs the User?

The navigation bar, the protected routes, the login page and three other pages all need the logged-in user. Passing it to each one as a prop would work, but every component in the way would have to carry it.

So far, every piece of state has belonged to one page. The ticket list holds its tickets; the detail page holds its ticket and comments. When two components needed the same thing, the page above them held it and passed it down as props (Stage 3, "The Page in the Middle").

The logged-in user is different. Eight components need something about it:

Component Needs For
App whether the session is still being checked topic 05
NavBar the user, their role, logout() the name, the Tags link, Log out
ProtectedRoute the user, their role who may open each page
LoginPage, RegisterPage the user, login() or register() logging in
HomePage the user "Log in" or "View the tickets"
TicketListPage their role the New ticket link
TicketDetailPage the user, their role Edit, Delete, and which comments can be deleted

With props

The page-in-the-middle answer would be to hold the user in the component above all of them, App, and pass it down:

The left-hand side would work. But:

  • App.jsx would hold the login code as well as the route table, and every route line would pass the same props, by name.
  • A component that only passes props on has to accept them anyway. If CommentList ever needed the user, TicketDetailPage would have to hand it over, and so would anything else in between.

This problem has a name, prop drilling: props drilled down through layers that don't use them.

With a context

The right-hand side is what Stage 4 does. A context holds a value that any component inside it can read directly, however deep it is. AuthProvider holds the user, and each component that needs it asks with one line, useAuth(). Nothing is passed down.

Try it

Find all eight for yourself:

grep -rn "= useAuth()" src --exclude="*.test.*"

For each line, look at what's inside { }. Does it match the table?
