Hardening

No new features: one hook instead of five copies of the same effect, an error boundary, an accessibility pass, a coverage report, the production build, nginx, and CORS.

  • What Stage 6 Adds

    What a stage with no new features is for, which parts apply to your own app, and which files change, before any of the code.

  • A Hook of Our Own

    The loading pattern every page has repeated since Stage 2, written once as a custom hook: useFetch.

  • Moving the Pages onto It

    Each page that loads data swaps its own effect for useFetch, keeps what's really its own, and passes every test it passed before.

  • When a Page Crashes

    A bug that throws while a page renders blanks the whole app. An error boundary, the app's one class, shows 'Something went wrong' instead.

  • An Accessibility Pass

    How to look for accessibility gaps, why an automated score isn't enough, and the three gaps this stage fills: page titles, a skip link and a table caption.

  • What the Tests Miss

    A coverage report shows which lines of the app no test has ever run. It found real gaps, and 16 new tests fill them, but 100% isn't the goal.

  • The Production Build

    What npm run build makes of the whole app: three files with the API's address written in, mostly React, and none of development's extra checks.

  • Serving It with nginx (Optional)

    The built app in a container: a two-stage Dockerfile, nginx sending the files, try_files for deep URLs, and a year's caching for files whose names change.

  • Pinning CORS

    The API lets every website call it from a browser. Listing the front-end's own origins is a back-end change: what it looks like, what the browser shows, and what it does and doesn't protect.

  • Making It Yours

    Trace questions for Stage 6, a checklist for hardening your own case study's front-end, and challenges to finish the course with.
