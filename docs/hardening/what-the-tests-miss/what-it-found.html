What It Found

The first report pointed at real behaviour that no test checked. Sixteen new tests fill those gaps.

The obvious place to add tests is the files with no test file of their own: TicketForm, CommentForm, tokenStorage, NotFoundPage. The report shows that's the wrong list. Those four were already at 100%, because the page tests run them, and check what they do, every time.

What the report found instead was behaviour no test had ever run:

Where What no test did New test
TicketFilters change Sort by or Order a new test file: each dropdown reports its own name
Pagination click Previous asks for the page before
TicketListPage choose "All statuses" again leaves status out of the query
TagsPage rename to a taken name; cancel a delete; a refused delete three tests
TicketDetailPage cancel a comment's delete; a refused (403) one two tests
EditTicketPage a save that fails stays on the form, shows the error
AuthProvider call register() saves the token, logs the user in
RegisterPage open it while logged in sends the user to the tickets
HomePage open it logged out shows Log in and Register
App load with a saved token not yet checked shows "Checking your session…"

That's 16 new tests: four in the new TicketFilters.test.jsx, and twelve added to existing files.

Gaps with consequences

Some of these are more than numbers. If someone renamed 'sortBy' to 'sort' in TicketFilters, the API would ignore the parameter, and the list would quietly stop sorting. Before, every test would still have passed. If register() stopped saving the token, a new user would be logged out by the next reload. Before, no test would have noticed. The report doesn't know which gaps matter, but it shows you where to look.

Choosing what to fill

Each row above is behaviour a user can see: a button, a message, a page. That's the test to write: not "line 47 ran", but "when the user does this, they see that". The coverage then follows.

Try it

Look at your own report again. Is there a component with no test file of its own that's still at 100%? Which page tests run it? Then find one gap that a user could actually hit, and write its test the way the table does: "when the user … they should see …".
