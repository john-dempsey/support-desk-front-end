Two of the New Tests

A component test for TicketFilters' dropdowns, and an App test that uses the real AuthProvider to catch the session check in progress.

Most of the 16 new tests follow patterns you already know. Two are worth a closer look.

A component on its own

TicketFilters only uses its props, so its tests render it with a fake onChange and check what it's called with, like Pagination's tests in Stage 3:

// Figure 6.34: Sort by (src/components/TicketFilters.test.jsx, excerpt)
  it('reports a new sort as "sortBy"', async () => {
    const handleChange = vi.fn();
    renderDefaultFilters(handleChange);

    await userEvent.selectOptions(
      screen.getByLabelText('Sort by'),
      'Subject',
    );

    expect(handleChange).toHaveBeenCalledWith('sortBy', 'subject');
  });

(The selectOptions line is split here to fit.) renderDefaultFilters() is a small helper in the same file that renders the dropdowns with the list's default choices. The test picks Subject by its visible text, as a user would, and checks the dropdown reported the API's own name for it, sortBy, with the value subject.

The real provider, caught in the middle

The "Checking your session…" screen only shows while AuthProvider is waiting for GET /auth/me. renderWithProviders uses a fake auth value, which is never checking anything, so this test uses the real AuthProvider instead:

// Figure 6.35: mid-check (src/App.test.jsx, excerpt)
  it('waits for a saved token to be checked before showing any page', () => {
    saveToken('saved-token');
    getCurrentUser.mockReturnValue(new Promise(() => {}));
    render(
      <MemoryRouter initialEntries={['/tickets']}>
        <AuthProvider>
          <App />
        </AuthProvider>
      </MemoryRouter>,
    );

    expect(screen.getByRole('status'))
      .toHaveTextContent('Checking your session');
    // Not sent to the login page while nobody knows yet who is logged in.
    expect(screen.queryByRole('heading', { name: 'Log in' }))
      .not.toBeInTheDocument();
  });

(The two expects are split here to fit.) Two tricks from earlier stages make it work:

  • saveToken() puts a token in localStorage before the app starts, so AuthProvider has something to check (Stage 4).
  • A promise that never resolves, new Promise(() => {}), keeps GET /auth/me waiting forever, so the test can look at the screen while the check is still running (the loading tests since Stage 2).

The second expect checks the reason the screen exists: without it, ProtectedRoute would send a logged-in user to the login page while their token was still being checked.

Try it

In TicketFilters.jsx, change onChange('sortBy', …) to onChange('sort', …) and run npm test. Exactly one test fails: which? Before Stage 6, how many tests would have failed? Put it back.
