What CORS Protects

CORS is a rule the browser follows for web pages. curl, a REST client and a WebSocket ignore it, so the token and authorize() are still what protect the API.

It's easy to think of pinned CORS as a lock on the API. It isn't. It's a rule that browsers follow, on behalf of the people using them.

What it doesn't stop

  • Anything that isn't a browser. CORS headers are only read by browsers. curl and your REST client ignore them: against an API pinned to 5173, curl still gets the full answer. Anyone can call the API that way, with or without your front-end.
  • The request itself, sometimes. A request that needs a preflight (one with a token, or a JSON body) is never sent. But a plain GET with no token isn't preflighted: it reaches the API, which runs it and answers, and only then does the browser refuse to hand the answer to the page.
  • The socket. CORS covers HTTP requests, not WebSockets. A page on any origin can open a WebSocket straight to Socket.IO, and it connects. What it can't do is join a user's room without that user's token: that's what the authenticate event checks (Stage 5).

What it does stop

Another website's page, opened in your user's browser, can't use your API from there and read the answers. That matters most when the browser sends something by itself with every request, such as a cookie. Stage 4 mentioned httpOnly cookies as the alternative to localStorage: an API that used them would rely on CORS (and the cookie's own settings) to stop other sites using a logged-in user's cookie. Our token is only sent because client.js adds it, and a page on another origin can't read our localStorage.

So what protects the data?

The same things as before: the token, checked by authenticate on every request, and authorize() checking the role. Pinning CORS is worth doing, because it's one less thing another website can do. But it adds to those checks. It doesn't replace any of them.

Try it

With your own back-end pinned to http://localhost:5173, run:

curl -i -H "Origin: http://evil.example" http://localhost:3000/tickets

(Use your own API's port and one of its routes.) What status comes back, and what does Access-Control-Allow-Origin say? Did CORS stop curl from reading it? What did stop it, if anything?
