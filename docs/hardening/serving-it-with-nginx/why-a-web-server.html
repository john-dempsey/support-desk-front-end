Why a Web Server

The built app is just files, so it needs a web server, not Node. The browser fetches the files from nginx and talks to the API itself.

This topic is optional. It needs Docker, as in back-end Lesson 6. If you don't have Docker, read it for the ideas and skip the Try its: nothing later in the course depends on it.

Back-end Lesson 6 put the API in a container, to show what running it "for real" looks like. This topic does the same for the front-end. But the two are very different things to run.

The API is a program. The front-end is files.

The API container runs node src/server.js: a program that answers every request by running code and asking MySQL.

After npm run build, the front-end is three files and an icon. No code runs on the server at all: every page is drawn by React in the browser. So the server only has to send files. That job needs no Node, just a web server. This topic uses nginx (said "engine X"), one of the most widely used.

The two containers never talk

The browser makes two kinds of request:

  1. For the app: index.html, the .js and the .css, from nginx on port 8080. Once they've arrived, nginx's job is done.
  2. For the data: every API call and the socket, straight from the browser to the API on port 3000, as it always has been.

So nginx never calls the API. Compare Lesson 6, where the api container reached MySQL as mysql:3306: there, one container really did talk to another, so they shared a Compose network. Here the API's address is the one the browser uses, so it stays http://localhost:3000, and the front-end's containers can run in a separate Compose stack from the API's.

Try it

Open the app on http://localhost:5173 with the Network tab open, and reload. Hover over the Name of a few rows to see their full address. Which requests went to port 5173 and which to port 3000? With nginx, the first group will come from port 8080 instead, and the second won't change.
