Keeping Files for a Year

A hashed file's contents never change, so the browser may keep it for a year. index.html is checked every time, so a new build is seen at once.

Stage 0 said the hash in index-CPcL75JA.js lets browsers know when to download a new version. npm run preview couldn't show it: it tells the browser to check every file. nginx can do better, with a second location in the same server:

# Figure 6.44: a year for the hashed files (nginx.conf, excerpt)
    # The JS and CSS from `npm run build`. A file's name has a hash in it
    # that changes whenever the build's content does, so a file with a
    # given name never changes: the browser may keep it for a year.
    location /assets/ {
        add_header Cache-Control "public, max-age=31536000, immutable";
        # A missing asset is a real 404, not index.html.
        try_files $uri =404;
    }
}

When more than one location matches the start of an address, nginx uses the longest. So addresses starting with /assets/ get these rules, and everything else gets location /'s.

  • max-age=31536000 is a year in seconds. immutable says the file will never change, so the browser doesn't even ask.
  • try_files $uri =404: a missing .js file is a real 404, not index.html pretending to be JavaScript.

Why it's safe

The two rules work together. index.html is sent with no-cache, so the browser checks it on every visit (nginx answers 304 Not Modified if it hasn't changed). A new build gives the .js a new name, and the new index.html points at it. The browser has never seen that name, so it downloads it. So users get a new build at once, and never download the same file twice.

Try it

Open http://localhost:8080 with the Network tab open, and reload. What does the Size column say for the .js and .css rows? Click the .js row and find Cache-Control under Response Headers. Now right-click the reload button (only while the DevTools are open) and choose Empty cache and hard reload: what changes in the Size column? Reload once more.
