Two Stages, One Small Image

The first stage uses Node to build the app. The second is nginx with dist/ copied in, and nothing else.

The Dockerfile sits in the app's own folder, like the API's. It has two stages. The first is the build:

# Figure 6.39: the build stage (Dockerfile, excerpt)
FROM node:22-alpine AS build
WORKDIR /app

# package files first, so Docker can reuse the `npm ci` layer when only
# the code has changed.
COPY package.json package-lock.json ./
RUN npm ci

COPY . .

# VITE_* values are written into the JavaScript when it's built, not read
# when the app runs. So the API's URL must be known now. .env isn't copied
# into the image (see .dockerignore), so compose.yaml passes it in as a
# build argument instead, and RUN sees it as an environment variable. If
# it's empty, client.js falls back to its default, as in `npm run dev`.
ARG VITE_API_URL
RUN npm run build

This is what you do by hand: npm ci, then npm run build, inside a Node container. (The next slide explains ARG.) The second stage takes only what that made:

# Figure 6.40: the serve stage (Dockerfile, excerpt)
FROM nginx:1.30-alpine

# Our settings replace nginx's default site (see nginx.conf for why).
COPY nginx.conf /etc/nginx/conf.d/default.conf
# The only thing taken from the build stage.
COPY --from=build /app/dist /usr/share/nginx/html

EXPOSE 80
# No CMD: the nginx image already starts nginx.

/usr/share/nginx/html is the folder the nginx image serves files from. The image you run is the last stage only: nothing from the first stage is in it except the dist/ folder copied across.

Compared with the API's Dockerfile

  • Both have two stages, for different reasons. The API's second stage still needed Node and node_modules to run. Ours needs neither: the final image has no Node, no node_modules and no source code. It's 93 MB, about the size of nginx's own image; the API's is 775 MB.
  • No USER line. Lesson 6 added USER node so the API doesn't run as root. The nginx image already takes care of this: its main process starts as root (so it can use port 80) and hands every request to worker processes that run as a user called nginx.
