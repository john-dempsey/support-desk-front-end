Changing It Later

Everything in the image is fixed when it's built. A change to the code, .env or nginx.conf needs --build; npm run dev stays how you work.

The image holds a finished build. Nothing in it watches your files, so nothing you change reaches port 8080 until the image is built again:

You change Port 5173 (npm run dev) Port 8080 (nginx)
a component shows it as you save docker compose up -d --build
.env's VITE_API_URL Vite restarts by itself docker compose up -d --build
nginx.conf (not used) docker compose up -d --build
nothing up -d alone keeps the running container

Without --build, docker compose up -d uses the image it already has, so the old build carries on. With --build, Docker reuses every step whose inputs haven't changed (Figure 6.39's comment on copying the package files first), so a rebuild after a code change skips npm ci and only runs npm run build again.

Which one to use

npm run dev stays how you work. It updates as you save, shows StrictMode's warnings and the error boundary's details, and runs no container. The nginx image is for checking the build the way users would get it, as npm run preview was, but with a real web server's rules: the try_files fallback, the caching headers and a real 404 for a missing asset.

It's also the step before putting the app online. A hosting service that runs containers could run this image as it is. Its address for the API would be the live API's, given to --build through .env.

Stopping it

docker compose down

in the app's folder stops and removes the container. The image stays, so the next docker compose up -d starts at once.

Try it

Change the text of the home page's <h1>, save, and look at ports 5173 and 8080. Run docker compose up -d --build and look again. In its output, find the npm ci step: does it say CACHED? Then put the heading back and build once more.
