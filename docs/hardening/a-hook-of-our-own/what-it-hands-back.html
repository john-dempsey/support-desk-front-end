What It Hands Back

useFetch returns an object of five values. A page takes the ones it needs, and can still change the data or ask again.

The hook ends by handing five things back to the page:

// Figure 6.5: what the hook hands back (src/hooks/useFetch.js, excerpt)
  function reload() {
    setReloadCount((currentCount) => currentCount + 1);
  }

  return { data, setData, error, isLoading, reload };
}

(The comment inside reload() is left out.)

Value What a page does with it
data shows it, once it isn't null
error shows error.message, or checks error.status
isLoading shows the Loading message while it's true
setData changes the data after a create, a delete or a push, without asking the API again
reload asks the API again, e.g. for a Reload button

An object, not an array

useState returns an array ([data, setData]), because it always returns exactly two things and you name them yourself. useFetch returns five, and most pages only need some of them. With an object, a page takes them out by name, in any order, the same as with useAuth() in Stage 4:

const { data, error, isLoading } = useFetch(getTags);

Why setData is handed back

Before, a page that created or deleted something changed its own state straight away, because it owned that state (Stage 3). Now the hook owns the data, so the page needs a way to change it. setData is just the hook's own setter, passed out. It works exactly like the setters the pages had before, function form included.

Why reload() uses the function form

reload() adds 1 to reloadCount, which runs the effect again: it's the counting part of Stage 5's handleReload(), moved into the hook. A page might call it after an await (later than the render it was made in), so it uses the function form, Stage 5's rule for any update worked out from the old state.
