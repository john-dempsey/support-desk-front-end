Testing the Hook

renderHook() runs a hook with no page around it, so the ignore flag finally gets a test of its own.

Because the pattern now lives in one place, it can be tested in one place, with no page and no faked API module. useFetch.test.js has six tests. Here's the first:

// Figure 6.6: loading, then data (src/hooks/useFetch.test.js, excerpt)
  it('is loading at first, then gives the data', async () => {
    const fetchTickets = vi.fn().mockResolvedValue(['first ticket']);

    const { result } = renderHook(() =>
      useFetch(fetchTickets, 'status=open'),
    );

    expect(result.current.isLoading).toBe(true);
    expect(result.current.data).toBeNull();
    await waitFor(() => expect(result.current.isLoading).toBe(false));
    expect(result.current.data).toEqual(['first ticket']);
    expect(result.current.error).toBeNull();
    expect(fetchTickets).toHaveBeenCalledWith('status=open');
  });

(The renderHook line is split over three lines here to fit.)

  • renderHook(), from Testing Library, runs a hook inside a tiny component of its own. result.current is whatever the hook returned on its latest render.
  • No vi.mock(). The hook is handed its API function, so the test hands it a vi.fn() instead. Passing the function in, rather than the hook importing it, is what makes this easy.
  • waitFor() keeps trying the check inside it until it passes (or gives up after a second). It's what findBy… does for elements, for any check at all.

The ignore flag, tested at last

Since Stage 0, the ignore flag has protected every page from a slow, out-of-date answer. No test checked it. Now one does. It needs an answer that arrives when the test says so:

// Figure 6.7: a slow answer (src/hooks/useFetch.test.js, excerpt)
function createSlowAnswer() {
  let finish;
  const promise = new Promise((resolvePromise) => {
    finish = resolvePromise;
  });
  return { promise, finish };
}

(Its comment is left out.) The finish it hands back is the promise's own resolve: calling it is what makes the answer arrive.

The test asks for ticket 1 (which gets the slow answer), then ticket 2 (which answers straight away), and only then finishes ticket 1's:

// Figure 6.8: ignoring a late answer (src/hooks/useFetch.test.js, excerpt)
  it('ignores a slow answer that arrives after a newer one', async () => {
    const slowAnswer = createSlowAnswer();
    const fetchTicket = vi.fn()
      .mockReturnValueOnce(slowAnswer.promise)
      .mockResolvedValueOnce({ id: 2 });
    const { result, rerender } = renderHook(
      ({ ticketId }) => useFetch(fetchTicket, ticketId),
      { initialProps: { ticketId: '1' } },
    );

    // Ticket 2 is asked for, and answers, before ticket 1 has answered.
    rerender({ ticketId: '2' });
    await waitFor(() => expect(result.current.data).toEqual({ id: 2 }));
    await act(async () => {
      slowAnswer.finish({ id: 1 });
    });

    // This is the `ignore` flag's job: ticket 1's late answer is dropped.
    expect(result.current.data).toEqual({ id: 2 });
  });

initialProps and rerender() pretend the page rendered again with a different ticket ID, as if the URL had changed. act() (Stage 5) lets React finish anything the late answer sets off before the last check.

The other four tests check an error, reload(), a new argument and setData.

Try it

In src/hooks/useFetch.js, take away the if (!ignore) around setData(result), leaving just setData(result);, and run npm test. Exactly one test fails: the one in Figure 6.8, with

AssertionError: expected { id: 1 } to deeply equal { id: 2 }

Ticket 1's late answer replaced ticket 2. That's the bug every page was protected from, now caught by a test. Put the if back and check everything passes again.
