Try It Yourself

Challenges that use everything in this lesson. Run the tests after each one, and commit when they pass.

Each of these builds on something from this lesson. After each one, run npm test and npm run lint, and commit when both pass.

Warm-up

  1. Your own skip link. If you haven't yet, add topic 05's skip link to your own app (the template doesn't have one). Write the test that checks it's the first link on the page (Figure 6.32).
  2. Two more tests. Two of the lines the coverage report still lists are worth a test. In useFetch.js, a stale error is ignored (the if (!ignore) around setError): test it the way Figures 6.7 and 6.8 test a stale answer. In client.js, the return null in readJson() runs when an answer's body isn't JSON (an HTML error page, say): test it with a stubbed fetch, as client.test.js does. Check each test fails when you remove the line it covers.
  3. [] instead of null. What would change if useFetch started data as []? Which pages would show something different while loading, and which tests would notice? Compare Stage 2's exercise (topic 07) on useState(null).

Build something

  1. Focus after navigation. When the user follows a link, a screen reader user hears nothing about the new page. Move focus to the page's <h1> after each navigation. Which component knows the path has changed? (The <h1> needs tabIndex={-1} to be focusable.) How would you test it?
  2. Try again. Add a Try again button to the error boundary's fallback that clears the error, so the page renders again without changing the path. When would trying again help, and when would it just crash again?
  3. Report it. Add a componentDidCatch(error, info) method to ErrorBoundary that logs info.componentStack. What extra does it tell you? A real app would send this to an error-reporting service.
  4. Automatic checks. Install vitest-axe and add an accessibility check to a few page tests. What does it find that topic 05 didn't? What did topic 05 find that it doesn't?
  5. One file for both stacks. Docker Compose's include: can pull another compose.yaml into this one. Use it to start the API's stack and the front-end's with one command. What has to be true about where the two folders are?

Investigate

  1. Two quick deletes. In TagsPage's handleDeleteTag, replace the function form with the plain setTags(tags.filter(…)). Create two new tags (both seeded tags are in use). In the Network tab, set throttling to the slowest preset, so the API's answers take a while. Delete the first new tag, then the second before the first answer arrives. When both have answered, what does the list show? Reload: what does the API say? Why does the function form fix it? Put the function form back and turn throttling off.
  2. Lazy loading. Our code is 9% of the bundle (topic 07). Read about React's lazy() and look at what it would split off. Is it worth it for this app? For what kind of app would it be?

Commit

git add .
git commit -m "Stage 6: hardening"

When your own case study's pages load their data through one hook, a crash shows a message instead of a blank page, every page has a title, the keyboard can skip the navigation, you know which code no test runs, and the built app works on its own, your front-end is finished.
