Not Every Effect Is a Fetch →

What Stays in the Page

The hook only loads. Deciding what an error means, the page's own notices, and the tags page's way of reloading all stay in the pages.

useFetch knows how to load one thing. It doesn't know what the thing is for, so anything that depends on this page stays in the page.

What an error means

The hook hands back the whole Error. Deciding what it means to the user is still the page's job, as it has been since Stage 2:

// Figure 6.15: not found (src/pages/TicketDetailPage.jsx, excerpt)
  const isNotFound = ticketError &&
    (ticketError.status === 404 || ticketError.status === 400);

(Split in two here to fit.) Another page could decide that a 404 means something else entirely, which is why it isn't in the hook.

The page's own state

The ticket pages' "this has changed" notice is their own state, hasChanged. In Stage 5 the effect's cleanup reset it. The hook's cleanup can't, since it doesn't know the notice exists, so each page resets it itself, at the moment it loads again:

// Figure 6.16: the notice (src/pages/TicketListPage.jsx, excerpt)
  function handleReload() {
    setHasChanged(false);
    reload();
  }

  // The new query loads fresh tickets, so any "have changed" notice is
  // out of date too.
  function changeSearchParams(newSearchParams) {
    setHasChanged(false);
    setSearchParams(newSearchParams);
  }

The filter and page handlers call changeSearchParams() instead of setSearchParams(). The ticket's page has a handleReload() like this one, which calls reloadTicket() and reloadComments(). (When the URL moves to a different ticket, the ticket's page starts afresh anyway, for a reason that comes later in this lesson.)

The tags page keeps its own reload

After adding or renaming a tag, the tags page loads the list again, because the API sorts tags by name. It doesn't use the hook's reload() for that:

// Figure 6.17: reloadTags() (src/pages/TagsPage.jsx, excerpt)
  // (Not useFetch's reload(): that would swap the list for "Loading tags…"
  // for a moment, and a failure wouldn't reach the form's error message.)
  async function reloadTags() {
    const latestTags = await getTags();
    setTags(latestTags);
  }

(Only the last two lines of the comment are shown.) reload() runs the effect again, and the effect's cleanup resets to "loading", so the list would vanish and the rename form with it. And a failed request would end up in the hook's error, not next to the form. Calling getTags() directly and handing the result to setTags avoids both.
