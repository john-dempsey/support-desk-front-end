Changing the Data Afterwards

After a create, a delete or a push, a page changes the loaded data with the setData the hook hands back, using the function form.

Loading is only half of what a page does with its data. After adding a comment, deleting a tag or receiving a push, the page changes what it loaded, without asking the API for everything again (Stage 3). Now the hook owns that state, so the page uses the setter the hook hands back, renamed to suit: setComments, setTags, setNotifications.

// Figure 6.14: adding a comment (src/pages/TicketDetailPage.jsx, excerpt)
  async function handleAddComment(commentText) {
    setCommentError(null);
    try {
      const newComment = await createComment(ticket.id, commentText);
      // ...
      setComments((currentComments) => [...currentComments, newComment]);
      return true;
    } catch (error) {
      setCommentError(error);
      return false;
    }
  }

(A long comment above setComments is left out.) It's the same [...] as Stage 3: a new array with the comment on the end.

The function form, wherever there's an await

setComments runs after an await, later than the render the handler was made in. Stage 5's rule says an update like that, worked out from the old state, uses the function form, so React hands it the list as it is now. Stage 6 applies that rule everywhere it fits:

Page Update Runs after
TicketDetailPage add a comment, delete a comment await createComment(…), await deleteComment(…)
TagsPage delete a tag await deleteTag(…)
NotificationsPage a push, Mark as read a socket event; await markNotificationRead(…) (both since Stage 5)

One new item in a dependency list

NotificationsPage listens for pushes in its own effect, which calls setNotifications. oxlint now asks for it in that effect's dependency list, [setNotifications]. It never asked for setNotifications when it came from useState in the page itself, because it knows React's setters never change. It can't see inside our hook, so it doesn't know this one never changes either. Listing it does no harm: it's the same function every render, so the effect still runs only once.

Try it

Before you try it, predict: two browser windows show the same ticket, logged in as the same user, and you add a comment in one. Will the other window show the new comment? Both pages call useFetch(getComments, …). (Think back to topic 02: what does each caller of a hook share, and what doesn't it? And Stage 5: is the author of a comment sent a notification about it?) Then try it.
