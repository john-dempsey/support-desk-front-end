What Was Already There

Most of the app's accessibility was built in from Stage 0. A checklist of what's already in place, and where each part came from.

The pass found three gaps, and that's all, because most of the work was done as each stage was built. Here's what was already in place, as a checklist you can hold your own app against:

In place Since
<html lang="en">, so a screen reader uses the right voice Stage 0
Semantic HTML: <header>, <nav>, <main>, one <h1> per page, <button> for actions and <Link> for navigation Stage 0
A clear focus outline on everything you can Tab to (:focus-visible) Stage 0
Every colour pair passes WCAG AA contrast Stage 0, checked again each stage
Loading messages in role="status", errors in role="alert" Stage 0
Status shown in words as well as colour (StatusBadge) Stage 1
Table headings with scope="col" Stage 1
A <label> for every input Stage 3
Field errors linked to their input (aria-describedby, aria-invalid) Stage 3
Repeated buttons told apart for screen readers ("Delete comment by Alex Agent") Stage 3 (and Stage 5's "Mark as read")
The unread count announced when it changes (aria-live="polite") Stage 5

Building it in is cheaper

Each line above cost a few characters when the component was written. Adding all of them to a finished app would mean revisiting every page. That's why Stage 0 called it "accessible by default", and why an accessibility pass at the end should find little.

It's also why the tests could check accessibility all along. Queries like getByRole('button', { name: 'Delete comment by Alex Agent' }) and getByLabelText('Subject') only find what a screen reader can find. A button with no name, or an input with no label, fails the test.

Try it

Go down the table with your own app open. For each line, find one place in your code where it's true, or note that it's missing. Which line was the hardest to check by reading the code, and how else could you check it?
