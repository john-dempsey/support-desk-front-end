Where It Goes

The boundary wraps the routes, inside main and below NavBar, and a key tied to the path gives every page a fresh start.

A boundary catches crashes inside it, so where it goes decides what survives a crash. App puts it around the routes:

// Figure 6.20: the boundary (src/App.jsx, excerpt)
  const location = useLocation();
  // ...
      <NavBar />
      <main id="main-content" className="container">
        {/* NavBar is outside the boundary, so it still works after a crash.
            key: React swaps in a new ErrorBoundary whenever the path
            changes, so going to another page clears the error. Without it,
            "Something went wrong" would stay on every page. */}
        <ErrorBoundary key={location.pathname}>
          <Routes>
            <Route path="/" element={<HomePage />} />
            {/* ... */}
          </Routes>
        </ErrorBoundary>
      </main>

(The id on <main> is for later in this lesson.) useLocation() comes from React Router: it returns the current URL, and location.pathname is its path, such as /tickets/2.

  • Inside <main>, below NavBar. Only the page is swapped for the fallback. The navigation, the user's name and Log out all keep working, so the user can go somewhere else.

Why the key

You met key in Stage 1, on list items: React uses it to tell components apart. When a component's key changes, React treats it as a different component: it throws the old one away, state and all, and makes a new one.

Once the boundary has caught an error, its state says so, and it shows the fallback whatever its children are. Without a key, clicking Tickets would change the route inside, but the same boundary, with the same error, would still be showing "Something went wrong". With key={location.pathname}, a new path means a new boundary, with error: null, so the next page appears as normal.

Everything inside starts afresh too

The new boundary brings new copies of everything inside it, including the page. So going from /tickets/1 to /tickets/2 now gives a brand new TicketDetailPage, with its notice and error messages back at their starting values. That's why topic 03 said the ticket's page "starts afresh anyway" when the URL moves to a different ticket. (Stage 2 showed React Router keeping the same page in that case. The boundary's key changes that, but useFetch's argument still lists the ticket ID, so the page would still be right without it.)

Only the path is in the key. A new filter on the list (/tickets?status=open) keeps the same path, the same boundary and the same page, which is why the list page resets its notice itself.

Try it

With the bug still in TicketDetailPage, open an unassigned ticket, then click Tickets in the navigation bar: the list appears. Now remove key={location.pathname} from the <ErrorBoundary> and reload. Open the unassigned ticket again and click Tickets. What do you see now, on the ticket list and every other page? Put the key back.
