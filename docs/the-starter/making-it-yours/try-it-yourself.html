Try It Yourself

Challenges that use everything in this lesson. Run the tests after each one, and commit when they pass.

Each of these builds on something from this lesson. After each one, run npm test and npm run lint, and commit when both pass.

Warm-up

  1. Rename the app. Change My App in NavBar.jsx and index.html to your case study's name. Which test, if any, needs to change?
  2. Break the connection. Stop your back-end and reload the page. What does the user see? Which file wrote that message? Which file decided where on the page it appears?

Build something

  1. An About page. Create src/pages/AboutPage.jsx with a heading and a short paragraph. Add a <Route> for /about in App.jsx and a <NavLink> in NavBar.jsx. Then write a test in App.test.jsx that checks the About heading shows at /about.
  2. A reusable component. Write src/components/PageTitle.jsx: a component that takes a title prop and returns <h1>{title}</h1>. Use it in HomePage, NotFoundPage and your About page. Do the existing tests still pass? Why?
  3. A second endpoint. Pick a simple GET endpoint from your own API. Add a function for it to a new src/api/*.api.js file, and show its result on your About page, using the three pieces of state and the useEffect pattern from HomePage. Test it with vi.mock, the way HomePage.test.jsx does.

Investigate

  1. Count the requests. Open the Network tab and reload the home page. How many times is /welcome requested? Why? Then try the same with npm run build and npm run preview. What changes, and why?
  2. Read the error. Make your API return an error for /welcome (for example, temporarily rename the route in your back-end). What does the front-end show now? Follow the message from your back-end's error handler to the screen, naming every file it passes through.

Commit

git add .
git commit -m "Starter: renamed, About page, ..."

Small, frequent commits make it easy to go back when something breaks, and they show how your work developed.
