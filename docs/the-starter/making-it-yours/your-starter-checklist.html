Your Starter Checklist

The first changes to make when the starter becomes your own case study's front-end, and the order to build the rest in.

The starter is the beginning of your front-end for Assignment 2, for your own case-study API. Before you add anything, make it yours.

1. Check it runs

npm install
cp .env.example .env    # change VITE_API_URL if your API isn't on port 3000
npm run dev

With your API running, the home page should say "The API says: Hello world!". Then run npm test (13 passing) and npm run lint (no output). If all three work, commit straight away, so you have a known good starting point to come back to.

2. Follow the TODOs

The starter marks every place you're expected to change with TODO (your case study). Search for it (Ctrl+Shift+F in VS Code). There are four:

File What to do
index.html change <title> to your app's name
src/components/NavBar.jsx change APP_NAME, and add a NavLink for each new page
src/App.jsx add a <Route> for each new page
src/api/welcome.api.js add a file like this for each of your own resources

3. Adding a page: always three steps

Every new page is the same three changes:

  1. The page: src/pages/BookingListPage.jsx, a component that returns its own <h1>.
  2. The route: <Route path="/bookings" element={<BookingListPage />} /> in App.jsx.
  3. The link: <NavLink to="/bookings">Bookings</NavLink> in NavBar.jsx, if it belongs in the navigation.

Then a test in App.test.jsx that checks it shows at its URL.

4. Build in stages

Don't try to build everything at once. Each step should run and pass its tests before the next one starts:

  1. Show your main entity with a list page and a detail page, using a hard-coded array before you fetch anything.
  2. Fetch it from your API with a new *.api.js file, and the three pieces of state from topic 06.
  3. Full CRUD: forms to create and edit, delete with a confirmation, and the API's validation messages next to each field.
  4. Login and roles, only if your API has authentication.
  5. Notifications, only if your API has them.

Steps 4 and 5 are optional. If your API stops at step 3, so does your front-end, and it's still a complete, working app.

The Support Desk worked example follows these same stages, one per lesson.
