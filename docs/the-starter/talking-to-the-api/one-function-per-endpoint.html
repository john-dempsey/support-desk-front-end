One Function per Endpoint

API modules give each endpoint a name, so pages ask for data without knowing any URLs.

apiRequest() knows how to talk to the API, but nothing about which endpoints exist. That's the job of the API modules: one file per back-end resource, with one function per endpoint. The starter has one:

// Figure 0.20: an API module (src/api/welcome.api.js, excerpt)
import { apiRequest } from './client.js';

export async function getWelcome() {
  const responseBody = await apiRequest('/welcome');
  return responseBody.data;
}

It does two small things:

  1. It knows the URL: /welcome. Pages call getWelcome() and never see it. If the back-end ever renamed the endpoint, this would be the only front-end file to change.
  2. It unwraps the envelope. The API sends { "data": { "message": "Hello world!" } }, but a page only cares about the inside, so getWelcome() returns responseBody.data: { message: 'Hello world!' }.

Errors don't need handling here. If apiRequest() throws, the error passes straight through getWelcome() to the page that called it.

Your own API modules

The comment at the top of this file has a TODO (your case study). For a bookings API, you'd add src/api/bookings.api.js, something like:

export async function getBookings() {
  const responseBody = await apiRequest('/bookings');
  return responseBody.data;
}

export async function getBooking(bookingId) {
  const responseBody = await apiRequest(`/bookings/${bookingId}`);
  return responseBody.data;
}

export async function createBooking(newBooking) {
  const responseBody = await apiRequest('/bookings', {
    method: 'POST',
    body: newBooking,
  });
  return responseBody.data;
}

Every function is short, and they all look alike. That's the point: client.js does the hard part once, and each endpoint gets a name that says what it does.

These files are the front-end's version of the back-end's services: the page (like a controller) decides what it needs, and the API module knows where to get it.
