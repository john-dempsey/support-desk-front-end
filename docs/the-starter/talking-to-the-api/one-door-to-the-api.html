One Door to the API

Why every request goes through one small module, and how the front-end's layers line up with the back-end's.

Every page that shows data has to talk to the API. The obvious way would be for each page to call the browser's fetch() function itself. The starter deliberately doesn't allow that. Every request goes through one door: the apiRequest() function in src/api/client.js.

Here's why. Talking to the API isn't one line of code. Each request has to:

  • add the API's base URL (http://localhost:3000) to the path
  • turn the request body into JSON, and say so in a header
  • add a login token, once the app has one
  • read the JSON that comes back
  • spot an error response, and dig the back-end's error message out of it
  • cope with the API not answering at all

If every page did all of that itself, the same code would be copied into every page, and every copy would be a chance for a mistake. Written once in client.js, it's tested once, and a fix in one place fixes it everywhere.

Three layers

The front-end splits the work into layers, just like the back-end did:

Front-end Its job Back-end equivalent
pages (HomePage.jsx) hold the data, decide what to show controllers
API modules (welcome.api.js) one function per endpoint, e.g. getWelcome() services
the client (client.js) the only code that calls fetch() Prisma: the only code that talks to the database

So a page never builds a URL or calls fetch(). It calls a function with a meaningful name, like getWelcome(). That function asks apiRequest() to do the HTTP work.

The client is also the mirror image of two back-end files. The back-end's utils/response.js wraps every success in { data } (or { data, meta }), and middleware/errorHandler.js wraps every error in { error: { message, details } }. client.js unwraps both shapes. The two ends of the conversation agree on one format, and each has one file in charge of it.

The rest of this topic goes through client.js from the moment a request is sent to the moment its answer comes back.
