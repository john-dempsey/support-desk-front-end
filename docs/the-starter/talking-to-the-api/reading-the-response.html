Reading the Response

Success, 204 No Content, and the error envelope: the three kinds of answer the API can give.

Once a response has arrived, apiRequest() decides what kind it is:

// Figure 0.16: making sense of the response (src/api/client.js, excerpt)
  if (response.status === 204) {
    return null;
  }

  const responseBody = await readJson(response);

  if (!response.ok) {
    const message =
      responseBody?.error?.message ||
      `Request failed with status ${response.status}`;
    throw createApiError(
      response.status,
      message,
      responseBody?.error?.details,
    );
  }

  return responseBody;
}

(The last two statements are split over several lines here to fit the page. Each is one line in the file.)

There are three possible outcomes.

1. 204 No Content: return null

The back-end answers a successful DELETE with 204 and no body at all. Calling response.json() on an empty body would fail, so this case is handled first: there's nothing to read, so the function returns null.

2. An error status: throw

response.ok is true for any status from 200 to 299, and false for anything else. When it's false, the back-end has sent its error envelope:

{ "error": { "message": "Validation failed", "details": [ ... ] } }

apiRequest() turns that into a JavaScript error and throws it, so the page that made the request ends up in its catch block. That's the same idea as throw new ApiError(...) in the back-end's controllers: an error stops the normal flow and goes to the code whose job is handling it.

The error is made by a small helper:

// Figure 0.17: an error with extra information (src/api/client.js, excerpt)
function createApiError(status, message, details) {
  const error = new Error(message);
  error.status = status;
  error.details = details;
  return error;
}

A plain Error only has a message. This one also carries the HTTP status (so a page can tell a 404 from a 400) and the details list from a validation failure (so a form can show each problem next to its field). It's a plain function, the same style as the rest of the starter, rather than a class.

3. Success: return the body

Anything else is a success, and the whole body ({ data } or { data, meta }) is returned.

?.: optional chaining

responseBody?.error?.message

?. means "if the thing on the left is null or undefined, stop and give undefined, instead of crashing". Without it, responseBody.error.message would throw a TypeError whenever an error response didn't use the expected envelope (for example, an error page from some other server). With it, the expression just gives undefined, and || falls back to a general message: Request failed with status 502.
