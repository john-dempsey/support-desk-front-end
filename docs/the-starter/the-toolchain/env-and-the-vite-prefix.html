.env and the VITE_ Prefix

Config works much like it did in the back-end, with one big difference: nothing in a front-end's .env is secret.

The front-end needs one setting: the address of the API. Like the back-end's PORT, it lives in a .env file, so it can change from one machine to another without editing code. And as in the back-end, .env is never committed (see .gitignore). .env.example is the committed template:

# Figure 0.4: the settings template (.env.example, excerpt)
VITE_API_URL=http://localhost:3000

The one file that reads it is the API client:

// Figure 0.5: reading the setting (src/api/client.js, excerpt)
const API_URL = import.meta.env.VITE_API_URL || 'http://localhost:3000';

Three things here are different from the back-end.

1. import.meta.env, not process.env

There's no process in a browser: it's a Node object, and the browser isn't running Node. Instead, Vite reads .env itself (no dotenv needed) and makes the values available as import.meta.env.

Vite doesn't look the value up while the app runs. It copies the value into your code when it sends the file to the browser (or, for npm run build, when it builds it). So when you edit .env, Vite has to start again to pick up the new value. It does that by itself: save .env and the terminal shows .env changed, restarting server.... Then reload the page.

2. Only VITE_ variables are exposed

Every value your front-end can read gets copied into JavaScript that is sent to the browser. Anyone using the app can open the developer tools and read it.

So Vite refuses to expose a variable unless its name starts with VITE_. That prefix is you saying "I know this will be public". It stops a database password, say, from leaking just because it happened to be in the same .env.

The rule this leads to: a front-end can't keep a secret. A URL is fine. A password or private API key never belongs in a front-end's .env, prefix or not. Secrets stay in the back-end.

(Laravel uses the same rule. Its default .env has a line VITE_APP_NAME="${APP_NAME}", which copies the app's name somewhere Vite is allowed to read it.)

3. A default instead of failing fast

The back-end's env.js stopped at startup if PORT was missing. Here, || 'http://localhost:3000' uses a default instead. A front-end has no startup step where it could stop with a clear message: by the time this line runs, it's already running in a user's browser. And localhost:3000 is the right answer for every student's machine in this module, so a fresh clone works even before you create .env.

Setting up a fresh clone

npm install
cp .env.example .env    # change VITE_API_URL if your API isn't on port 3000
npm run dev

Try it

With both projects running, change VITE_API_URL in .env to http://localhost:3001 and save. Watch Vite's terminal, then reload the page. What message do you see, and which file wrote it? Put the value back when you're done.
