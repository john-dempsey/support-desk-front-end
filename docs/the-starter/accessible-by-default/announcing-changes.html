Announcing Changes

A single-page app changes the page without loading a new one, so it has to tell screen readers when something new appears.

When a Laravel app loaded a new page, a screen reader noticed and started reading it. A single-page app changes part of the page instead: a loading message appears, then an error, then the data. A screen reader user isn't looking at the screen, so unless something tells them, they don't know anything has changed.

Live regions fix that. An element with one of these roles tells screen readers: "announce what appears in here".

The starter's two shared message components each use one:

// in Loading.jsx (Figure 0.9)
<p role="status" className="loading">
  {message}
</p>

// in ErrorMessage.jsx (Figure 0.8)
<p role="alert" className="error-message">
  {message}
</p>

status and alert

  • role="status" is polite. The screen reader waits until it has finished what it's saying, then reads the message. Right for "Connecting to the API…": useful, but not urgent.
  • role="alert" is assertive. The screen reader interrupts what it's saying to read the message straight away. Right for errors, which the user needs to know about now. Keep it for real problems: being interrupted all the time is as annoying as it sounds.

Why this is in shared components

Because Loading and ErrorMessage are components, the right role is written once. Every page that uses them gets the announcements without having to remember. That's the same argument as client.js in topic 05: put the detail that's easy to get wrong in one place.

Roles and tests

These roles are also how the starter's tests find these messages: screen.getByRole('status') and screen.findByRole('alert'). A test that finds things the way a screen reader does checks accessibility for free. The testing topic explains that next.
