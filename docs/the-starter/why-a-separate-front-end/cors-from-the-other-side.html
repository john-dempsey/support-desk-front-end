CORS From the Other Side

You added cors() to the API in Lesson 6. This is the browser's side of that story, and what it looks like when it goes wrong.

In the back-end's Lesson 6 you added one line to app.js:

app.use(cors());

At the time there was no front-end to show why. Now there is.

An origin is a scheme, a host and a port together. The front-end's page comes from http://localhost:5173. The API is at http://localhost:3000. The port is different, so to the browser these are two different origins, even though both are on your own machine.

By default, a browser won't let a page read a response from a different origin (the Same-Origin Policy). It makes an exception only if the response includes a header that says it's allowed:

Access-Control-Allow-Origin: *

That header is what cors() adds to every response. * means "any origin may read this", which is fine while there's no deployed front-end to restrict it to.

When it goes wrong

If the API didn't send that header, the request would still reach the API, but the browser would refuse to hand the response to your JavaScript. The browser's Console would show a red error containing the words "blocked by CORS policy".

Your code doesn't get a status code or an error message from the API in that case: as far as it can tell, no response arrived at all. So the front-end shows the same message it shows when the API isn't running:

Can't reach the API at http://localhost:3000 — is the back-end running?

If you see that message and the API is running, open the browser's developer tools (F12) and check the Console. A CORS error there means the problem is the API's headers, not your front-end code.

Try it

With both projects running, open the developer tools, go to the Network tab, and reload http://localhost:5173. Click the request to welcome and look at its Response Headers. Can you find Access-Control-Allow-Origin? Which line of the back-end put it there?
