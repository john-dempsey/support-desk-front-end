From Blade to a Client App

In Laravel the server built every page. Your API doesn't build pages at all, so the browser has to.

In Year 2, every page your Laravel app showed was built on the server. A request came in, a route sent it to a controller, the controller loaded some models and handed them to a Blade view, and Blade turned them into a complete HTML page:

// Laravel: the server returns a finished page
public function index()
{
    $tickets = Ticket::all();
    return view('tickets.index', ['tickets' => $tickets]);
}

The browser's only job was to display that HTML. Clicking a link sent a new request, and the server built and sent a whole new page.

The Support Desk API you built in Node works differently. It never returns HTML. Ask it for GET /tickets and you get JSON:

{ "data": [{ "id": 1, "subject": "Cannot log in", "status": "open" }] }

That's ideal for a program, but it isn't a page anyone can use. Something has to take that JSON and turn it into headings, tables, buttons and forms. In this module that something is a JavaScript program running in the browser: the front-end, or client.

A single-page application

The front-end you'll build is a single-page application (SPA). The browser loads one HTML page, once. From then on, JavaScript does what the server used to do:

  • it asks the API for data (JSON) when a page needs it
  • it builds the HTML for that data in the browser
  • when you click a link, it swaps what's on screen without asking the server for a new page

To build it you'll use React, a JavaScript library for building user interfaces out of small, reusable pieces called components. You've never used a front-end library like this before, so this lesson introduces React from the start.

Laravel + Blade API + React
Who builds the HTML? the server, using Blade the browser, using React
What the server sends a finished HTML page JSON data
Clicking a link a new request and a whole new page JavaScript changes part of the page
Where page logic runs PHP, on the server JavaScript, in the browser

Why split it in two?

  • One API, many clients. The same API can serve this website, a mobile app, or another company's system, because it only deals in data.
  • Separate jobs. The back-end owns the data and the rules; the front-end owns what the user sees. Each can be changed, tested and deployed on its own.
  • A smoother experience. Only the part of the page that changes is redrawn, so moving around the app feels quicker than reloading every page.
