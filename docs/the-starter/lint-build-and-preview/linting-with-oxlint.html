Linting With oxlint

A tool that reads your code without running it and points out likely mistakes, including breaking the rules of hooks.

A linter reads your code without running it and points out things that are probably mistakes: a variable you never use, a hook called in the wrong place, a comparison that can never be true. Think of it as a spell-checker for code. It finds a whole class of bugs in seconds, before you've even opened the browser.

The starter uses oxlint, the linter in the current Vite React template. Run it with:

npm run lint

If there's nothing to report, it prints nothing.

The settings

// Figure 0.32: the linter's settings (.oxlintrc.json)
{
  "$schema": "./node_modules/oxlint/configuration_schema.json",
  "plugins": ["react", "oxc"],
  "rules": {
    "react/rules-of-hooks": "error",
    "react/only-export-components": [
      "warn",
      { "allowConstantExport": true }
    ]
  }
}

(The last rule is one line in the file, spread over four here to fit.)

oxlint has a sensible set of rules turned on already. This file adds the React plugin and two React rules on top:

  • react/rules-of-hooks (an error) enforces topic 06's rule: hooks are called at the top level of a component, never inside an if or a loop.
  • react/only-export-components (a warning) checks that a .jsx file exports only components. Vite's Fast Refresh (topic 02) can only update a component in place if its file exports nothing else. allowConstantExport makes an exception for constants.

What an error looks like

Suppose a component calls useState inside an if:

import { useState } from 'react';

function Example({ showCount }) {
  if (showCount) {
    const [count] = useState(0);
    return <p>{count}</p>;
  }
  return null;
}

npm run lint reports (on one long line, split here to fit):

src/pages/Example.jsx:5:21: error react-hooks(rules-of-hooks):
React Hook "useState" is called conditionally. React Hooks must be
called in the exact same order in every component render. help: Move
the Hook call before the condition, or call it unconditionally and
branch inside the Hook/effect instead.

It gives the file, the line and column, which rule failed, why the rule exists, and a hint for fixing it.

When to run it

Before every commit, together with npm test. Many editors (VS Code with the oxc extension, for example) can also show these problems as you type, underlined in the code.
