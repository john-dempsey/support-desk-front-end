Three Pieces of State

A page that loads data has to remember three things: the data, any error, and whether it's still waiting.

HomePage asks the API for its welcome message. While it waits, and after the answer arrives, the page has to remember three things:

// Figure 0.21: the page's state (src/pages/HomePage.jsx, excerpt)
function HomePage() {
  const [welcome, setWelcome] = useState(null);
  const [errorMessage, setErrorMessage] = useState('');
  const [isLoading, setIsLoading] = useState(true);
State Starts as Why that starting value
welcome null there's no data until the API answers
errorMessage '' (empty) nothing has gone wrong yet
isLoading true the request starts as soon as the page appears, so it's waiting from the very start

Between them, they describe every moment in the page's life:

  1. Waiting: isLoading is true, the other two are empty.
  2. Success: welcome holds the data, isLoading is false.
  3. Failure: errorMessage holds the reason, isLoading is false.

Each one gets its own useState, with a name that says what it holds. The names matter: isLoading reads like a yes/no question, which is exactly what it is.

The pattern you'll repeat

Every page that loads data from the API needs these same three things: the data, an error message, and a loading flag. A ticket list page would have tickets instead of welcome; a booking page would have booking. The other two stay the same. When you write your own pages, start with these three lines.

Compared with Laravel

In Laravel the controller waited for the database, then passed finished data to the view, so a Blade view never had a "still loading" moment. In the browser, the page appears first and the data arrives later, so the page has to describe what to show in the meantime. That's why the loading state exists at all.
